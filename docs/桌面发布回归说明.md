# 桌面发布回归说明

这份说明针对当前仓库的桌面版交付流程。

## 目标

把下面几段验证收成一条固定流程：

1. 打包配置静态检查
2. backend 回归
3. 前端构建
4. Python sidecar 打包
5. Tauri release 包构建
6. `.app`、`.dmg`、sidecar 产物检查
7. `.app` 重签和开发机路径扫描
8. sidecar 健康检查和退出检查
9. `.app` bundle 启动检查

## 命令

```bash
npm run verify:desktop
```

这条命令会调用 [scripts/verify-desktop-release.sh](../scripts/verify-desktop-release.sh)。

## 脚本会做什么

### 1. 打包配置静态检查

执行：

```bash
npm run verify:packaging-static
```

这一步检查内置 Embedding 模型文件、前端静态回归、API / local smoke、模型预检、macOS / Linux 和 Windows sidecar 打包脚本、macOS release 发布验证脚本、Windows 发布验证脚本以及 GitHub Actions 工作流中的关键步骤，确认 `BAAI/bge-small-zh-v1.5` 模型目录、`fastembed / onnxruntime / tokenizers` 运行依赖、sidecar 健康检查、macOS 路径重映射和 NSIS 构建命令没有从脚本里消失。

这是静态检查，不会生成 Windows 安装包，也不能替代 Windows 实机安装、卸载和首次启动验收。

### 2. backend 回归

执行：

```bash
npm run backend:test
```

当前应通过全部 Python 单测。

### 3. 前端构建

执行：

```bash
npm run build
```

用于确认 Vue 模板、运行时 API 和技能区界面没有编译问题。

### 4. 打包 Python sidecar

执行：

```bash
npm run backend:bundle
```

会生成 `src-tauri/binaries/novel-backend-*`。

如果当前 Python 环境安装了 LiteParse，sidecar 打包脚本会把 `liteparse` 的 native 扩展和 PDFium 动态库一起收进产物；验证 PDF 导入时要覆盖 LiteParse 可用、LiteParse 失败回退到 `pypdf`、本地文本为空后再尝试 OCR 这三种路径。

sidecar 打包脚本会把 `backend/novel_backend/assets/embedding_models` 里的内置 `BAAI/bge-small-zh-v1.5` 模型收进产物，并收集 `fastembed`、`onnxruntime` 和 `tokenizers` 运行依赖。发布前需要确认本地 Embedding 在离线环境下能生成 512 维向量。

### 5. 验证 sidecar 可用

脚本会直接拉起打包出来的 sidecar，检查：

- `GET /api/app/health`
- `POST /api/config/test`，只测内置本地 Embedding，要求 `BAAI/bge-small-zh-v1.5` 返回 512 维
- `POST /api/app/shutdown`

这一步不是查文件存在，而是真的把产物跑起来，并确认打包后的 backend 能加载随包内置的 Embedding 模型。PyInstaller onefile 首次冷启动可能需要解包，健康检查最多等待 120 秒；如果进程在健康检查前退出，脚本会打印退出码和 sidecar 日志。

Tauri 壳退出时会先请求 `POST /api/app/shutdown`，给 backend 写完状态的机会，然后再结束 sidecar。macOS 生产包启动时还会检查同一 `.app/Contents/MacOS/novel-backend` 路径下父进程已失效的旧 sidecar，并清理这些孤儿进程，避免多次启动后积累后台 backend。

### 6. 构建 Tauri release 包

脚本默认执行带 Rust 路径重映射的 release 构建。手工单独执行 Tauri 构建时也要带同样的路径重映射：

```bash
RUSTFLAGS="--remap-path-prefix=$(pwd)=/workspace --remap-path-prefix=$HOME=/home" npm run tauri -- build
```

需要临时验证 debug 包时可执行：

```bash
TAURI_BUILD_PROFILE=debug npm run verify:desktop
```

release 产物默认在：

- `src-tauri/target/release/bundle/macos/稿匣.app`
- `src-tauri/target/release/bundle/dmg/*.dmg`

### 7. 检查应用内 sidecar

脚本会继续验证：

- `.app` 本体存在
- `.app/Contents/MacOS/novel-backend` 存在且可执行
- `dmg` 产物存在
- `.app` 主程序和 sidecar 不包含开发机用户目录或项目绝对路径
- 如果当前环境有 `codesign`，会先调用：

```bash
npm run desktop:resign
```

这一步会补齐 `Contents/Resources`，再对当前 `.app` 重新签名。

- 然后执行：

```bash
codesign --verify --deep --strict
```

### 8. 运行应用内 sidecar

最后会直接拉起 `.app` 里的 sidecar 再做一次健康检查、本地 Embedding 配置测试和退出检查，同样给冷启动最多 120 秒，并在进程提前退出时打印日志。

### 9. 验证 `.app` bundle 启动

脚本会读取 `.app/Contents/Info.plist` 里的 `CFBundleExecutable`，通过 `open -n 稿匣.app` 按 macOS 正常 app bundle 方式启动应用，找到新启动的主进程后观察 10 秒。验证结束后会结束主进程，并清理同一个 app bundle 下的 `novel-backend` sidecar 进程。

如果 setup 阶段 panic、sidecar 查找失败、主进程没有保持运行或启动后提前退出，脚本会打印 `app-launch.log` 并失败。

## 当前覆盖范围

这条脚本覆盖 macOS 开发环境上可自动化的桌面回归。

已经覆盖：

- backend 单测
- 前端构建
- 打包配置静态检查
- sidecar 打包
- Tauri release 构建
- `.app`、`.dmg`、sidecar 产物检查
- `.app` 重签、签名校验和开发机路径扫描
- sidecar 运行级健康检查和本地 Embedding 加载检查
- `.app` bundle 启动检查

还没覆盖：

- GUI 自动化点击回归
- macOS notarization
- Windows 安装后 GUI、安装卸载和签名验收
- Linux 实机打包验证
- 扫描版 PDF 的 OCR 导入

## Windows 打包

Windows 安装包不在 macOS 本机生成。仓库新增了手动触发的 GitHub Actions 工作流：

```text
Windows Desktop Release
```

它在 `windows-latest` runner 上执行：

1. 安装 Node.js 20、Python 3.12 和 Rust stable
2. 安装前端依赖、backend 依赖和 PyInstaller
3. 运行 Windows backend 单测
4. 构建前端
5. 打包 `src-tauri/binaries/novel-backend-x86_64-pc-windows-msvc.exe`
6. 拉起 Windows sidecar 做健康检查和退出检查
7. 执行 `npm run tauri -- build --bundles nsis`
8. 上传 NSIS `setup.exe` 和 Windows sidecar

本地 Windows 机器也可以执行：

```powershell
npm run verify:desktop:windows
```

产物默认在：

- `src-tauri/target/release/bundle/nsis/*.exe`

这条链路能确认 Windows sidecar 能运行、Tauri 能生成 NSIS 安装包；还不能替代人工安装、卸载、首次启动、杀毒软件拦截和代码签名验证。MSI 需要单独处理 WiX 构建后再纳入 CI 产物。

## 什么时候跑

建议这几种改动都跑一遍：

- 改了 `src-tauri`
- 改了 backend 启动参数
- 改了 sidecar 打包脚本
- 改了前端运行时地址或桌面启动链
- 准备出一个可交付包之前

## 临时测试分发

如果暂时没有 Apple Developer Program 账号，仓库也支持一条测试版临时分发流程。

执行：

```bash
npm run package:test:macos
```

或者从回归到打包一次做完：

```bash
npm run release:test:macos
```

脚本会把已经生成的 `dmg` 连同下面这些文件一起整理到 `release/test-release/macos/`：

- `安装说明-先看这个.md`
- `测试反馈清单.md`
- `SHA256SUMS.txt`
- `包信息.txt`

这条流程的边界：

- 不是 notarized 包
- 需要测试用户手动放行第一次启动
- 只适合受控测试

## 签发测试许可证

外部测试包使用离线 Ed25519 签名许可证，不需要部署服务器。

生成一对签发密钥：

```bash
scripts/generate-license-keypair.py \
  --private-key-file ~/.gaoxia-license/ed25519-private-key.json \
  --public-key-file ~/.gaoxia-license/ed25519-public-key.txt
```

应用内置公钥后，用私钥签发测试许可证：

```bash
scripts/create-license.py \
  --private-key ~/.gaoxia-license/ed25519-private-key.json \
  --licensee "测试用户" \
  --expires-at "2026-06-30T00:00:00Z"
```

永久许可证使用 `--permanent`：

```bash
scripts/create-license.py \
  --private-key ~/.gaoxia-license/ed25519-private-key.json \
  --licensee "测试用户" \
  --permanent
```

如果要绑定设备，先让测试用户在许可证面板复制“当前设备码”，再追加：

```bash
--device-fingerprint "<设备码>"
```

设备绑定可以和限时许可证、永久许可证同时使用。

私钥不要提交到仓库，也不要放进安装包。
