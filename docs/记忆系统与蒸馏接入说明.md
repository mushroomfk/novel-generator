# 记忆系统与蒸馏接入说明

本文记录项目记忆和结构化蒸馏的接入方式，核心能力有两部分：

1. 分层记忆
2. 结构化蒸馏

没有引入多用户画像、长期陪聊调度器或会话归档系统。当前项目是小说生成器，重点放在作品上下文、章节连续性和作者确认后的经验沉淀。

## 1. 当前已经接入的能力

### 项目记忆

- 项目记忆现在分成两层：
  - `manual_entries`
    作者手工维护，写明确规则、底线、偏好、阶段目标
  - `derived_entries`
    系统根据章节、架构文件、人物和世界要素自动整理
- 兼容索引仍保存在项目根目录下的 `project_memory.json`。
- 可读写正文已经拆到 `project_memory/` 目录，方便人工查看、编辑和版本管理。
- 旧格式 `entries` 会在读取时自动迁移，不需要手工处理历史项目。

### 文件型项目记忆

新的本地文件结构参考了 Claude Managed Agents Memory 的做法，但不依赖 Anthropic 服务。

```text
project_memory/
  author/
    canon/          作者写下的硬规则
    style/          作者偏好
    continuity/     作者指定的连续性要求
    warnings/       作者提醒不要写偏的内容
    planning/       作者指定的阶段目标
  system/
    canon/          系统整理的世界规则
    style/          系统整理的意象词场
    continuity/     系统整理的人物现状、最近推进、关键要素
    warnings/       系统整理的未解悬念
    planning/       系统整理的当前阶段目标
  audit.jsonl       每次记忆文件变化的审计记录
```

每条记忆是一份 markdown 文件，头部带 `id`、`title`、`category`、`source`、`updated_at`。后端读取项目详情时会优先读取这些 markdown 文件，再回到 `project_memory.json` 做兼容。这样直接改记忆文件，也会进入后续上下文。

手工记忆通过界面保存时，会更新 `project_memory/author/`。系统整理通过项目内容刷新时，会更新 `project_memory/system/`。后端写入或下次读取发现外部编辑时，会把文件新增、修改、删除记录到 `audit.jsonl`。

### 自动化策略

项目记忆现在不需要额外手工刷新。以下动作完成后，会自动刷新系统记忆，并把梦境候选写入 `project_memory/system/`：

- 保存章节正文
- 清空章节正文
- 保存设定文件
- 批量应用整书架构
- 导入参考资料
- 保存作者记忆
- 手动运行做梦整理

自动回流只写入 `system` 侧记忆，不会写进 `author` 侧。也就是说，模型或规则整理出来的东西只会被标成“系统整理”，不会冒充作者明确要求。

### 自动整理规则

系统会从现有项目内容里整理这些信息：

- 世界规则
- 主要人物现状
- 最近推进
- 关键要素
- 别丢的悬念
- 当前阶段目标
- 当前意象词场

这些内容是确定性整理，不依赖额外模型，读项目就能生成。

### 上下文注入

项目记忆已经进入这些链路：

- `build_project_context_bundle`
- 分步架构 `architecture_step`
- 章节工作流
- 继续扩写
- 蓝图生成
- brainstorming

进入提示词时会区分来源：

- `作者明确要求`
- `系统整理`

这样模型能分清哪些是作者硬要求，哪些是系统从项目里归纳出来的上下文。

### 文风参考库蒸馏

- 每个文风方案会从作者参考库生成一段 `reference_distillate`
- 这段蒸馏不是替代原文片段，而是作为参考库的压缩说明
- 现在会同时进入：
  - `build_style_reference_text()`
  - 文风校准提示词 `_style_detail_prompt()`
  - 文风详情面板展示

蒸馏内容目前主要包括：

- 高频词场
- 句式和节奏参考
- 反复出现的意象或表达重心

### 项目蒸馏持久化

- `get_project_detail` 会返回当前可用的项目蒸馏报告；缺失或过期时可以即时生成用于展示和上下文组装。
- 详情读取本身不再写入新的 `project_distillation.json`。
- 保存章节、保存设定文件、导入资料、刷新系统记忆等会改变项目内容的动作，会负责保存后续要复用的蒸馏结果。

### Agent 经验候选与自学习复盘

- Agent 执行结束后会做一次确定性复盘，生成 `learning_review` 产物。
- 经验候选会记录到项目目录下的 `.gaoxia/learning/reviews.jsonl`。
- 当前会整理三类内容：
  - 讨论结论里可长期复用的目标、偏好或约束
  - 资料分析结果里可能影响后续架构或续写的结论
  - 已被建议保存为用户技能的重复处理方式
- 自学习复盘会生成 `self_evolution_review` 产物，并维护这些项目级文件：
  - `.gaoxia/learning/self_evolution_candidates.json`
  - `.gaoxia/learning/self_evolution_reviews.jsonl`
  - `.gaoxia/learning/agent_capability_rules.json`
  - `.gaoxia/learning/writing_evaluations.jsonl`
  - `.gaoxia/learning/self_evolution_drafts.json`
  - `.gaoxia/learning/writing_regression_runs.jsonl`
  - `.gaoxia/learning/self_evolution_model_reviews.jsonl`
  - `.gaoxia/learning/failure_cases.jsonl`
  - `.gaoxia/learning/self_evolution_schedule.json`
- 技能使用统计和整理报告保存在应用数据目录：
  - `skills/.usage.json`
  - `skills/.curator_reports.jsonl`
- 技能版本快照保存在应用数据目录：
  - `skills/.versions/{skill_id}/versions.json`
  - `skills/.versions/{skill_id}/{version_id}.md`
- 第二审查模型配置保存在 `app_config.json` 的 `review_model` 字段；环境变量仍可覆盖本地配置。
- `agent_capability_rules.json` 和 `failure_cases.jsonl` 会进入后续 Agent 的模型路由和模型规划上下文，用来影响 action 顺序、工具选择和失败前检查。
- 章节低分核验和自动修订会生成额外的技能候选，用于沉淀“章节低分修订经验”。
- 这部分不会自动写入 `project_memory/author/`，也不会自动改章节正文。候选被作者标为已采纳后，会生成待确认草案；草案应用后才会写入作者侧项目记忆、创建或更新用户技能，或把调用规则标为作者采纳。
- Agent 的完整执行轨迹另存到应用数据目录下的 `logs/agent_trajectories.jsonl`，可以通过 `GET /api/studio/agent-trajectories` 查看。
- 技能库 `Agent 自学习` 面板可以查看能力看板、确认草案、候选、调用规则、写作评价、写作回归、模型审查、失败案例、重复失败聚合、长期趋势、细分质量维度、技能统计、技能版本和技能包，也可以调整候选状态、触发技能库状态检查、保存排程、手动执行排程任务、回滚技能版本、导入导出技能包或把用户技能提升为全局技能。
- 多模型交叉审查默认不启用；设置页启用并填写完整配置，或配置 `NOVEL_REVIEW_MODEL_API_KEY`、`NOVEL_REVIEW_MODEL_BASE_URL`、`NOVEL_REVIEW_MODEL_NAME` 后，模型审查会增加第二审查模型结果。

### 自我进化报告

技能区 `自我进化` 读取 `GET /api/studio/self-evolution?project_id=...`，把以下内容放到同一个报告里：

- `.gaoxia/learning/reviews.jsonl` 里的记忆候选和技能候选
- `logs/agent_trajectories.jsonl` 里的失败执行样本
- 章节产物 metadata 里的核验低分、风险状态和自动修订记录
- `logs/prompt_history.jsonl` 里的模型调用失败记录
- `skills/` 和 `.skill_usage.json` 里的技能使用状态

报告候选分为 `skill / memory / prompt / review` 四类。`memory` 仍需作者确认后才能进入作者记忆；`skill` 仍需通过用户技能沉淀入口创建或更新 `SKILL.md`；`prompt` 和 `review` 用作后续提示词或章节质量评测样本。

## 2. 为什么这样接

- 小说项目最容易爆的是上下文长度，不是用户画像。
- 对章节生成真正有价值的是“近期推进、人物现状、别丢的悬念、当前阶段目标”这类项目态信息。
- 文风部分真正值得蒸馏的是“作者参考库里的共性写法”，不是泛化的用户画像。

当前接法保留对小说写作最有价值的部分，同时避开对项目帮助不大的重型模块。

## 3. 前端行为变化

- `项目记忆` 面板拆成两块：
  - `作者明确要求`
    可编辑、可保存
  - `系统整理`
    只读，跟随项目内容自动刷新
- `文风详情` 面板新增 `参考库蒸馏` 展示，方便直接看当前参考库收敛成了什么。
- Agent 消息产物区会展示 `经验候选` 和 `自学习复盘`，标出候选、规则和评分信息，避免把临时讨论直接写进作者记忆。
- Agent 写回章节正文时会默认串起正文生成、去 AI 改稿和一致性复查；章节工作流里的 draft 写回和单独改稿也会进入同一套复查链路。章节写回后触发系统记忆刷新，章节核验报告会作为产物进入消息区，方便作者决定是否继续改。
- 技能库新增 `Agent 自学习` 面板，候选采纳后不会直接写记忆或技能，而是进入确认草案区；写作回归、模型审查、排程、趋势、失败案例、草案差异、技能版本、技能包迁移也在这里查看或处理。

## 4. 后续继续做时的方向

如果还要往前走，优先级建议这样排：

1. 把自动记忆接进章节生成后的回写链路，按章节增量刷新，而不是只在读取项目详情时刷新
2. 给自动记忆加更细的权重和过期策略，减少旧悬念长期占位
3. 把参考库蒸馏再拆细一点，区分叙述视角、句长节奏、对白密度、信息释放方式
4. 再考虑是否需要引入基于模型的反思摘要；当前这一步先不急

## 6. 做梦机制

### 接入方式

- 项目根目录新增 `project_dreams.json`
- 每次“做梦”都会产出一份最近梦境报告，结构包括：
  - `summary`
  - `themes`
  - `insights`
  - `open_questions`
  - `memory_candidates`
- 这份报告不会自动改正文。
- 候选会自动写入系统侧项目记忆，不再需要手工点选。

### 为什么这样接

- 做梦机制更像慢路径整理和受控回流，不是自动续写。
- 小说项目最怕的是“梦境结果直接污染正文”。
- 所以目前只把梦境结果接给规划类能力：
  - `brainstorm`
  - `blueprint`
  - `continue-project`
  - `architecture-step`

正文生成、章节续写、改稿都不吃梦境摘要。

### 结果怎么产生

- 有可用模型时：
  - 走模型版做梦，输出结构化 JSON 报告
- 没配模型，或者模型调用失败时：
  - 自动回退到规则版做梦
  - 依然会根据最近推进、悬念、人物现状和阶段目标生成一份可读报告

### 过期规则

- 梦境报告会记录自己的 `source_signature`
- 只要章节正文或项目设定文件变了，旧梦境就会被标记为 `is_stale`
- 过期后的梦境结果：
  - 不再进入规划类提示词
  - 仍然可以展示给作者看
  - 但建议先重跑一轮

### 前端入口

- `Story Overview -> 梦境整理`
- 这里可以：
  - 手动触发一轮做梦
  - 查看最近梦境摘要、慢线索判断、待验证问题
  - 把某条候选写回项目记忆

### 当前边界

- 现在还是手动触发，不是定时调度
- 梦境候选默认写入 `system` 侧项目记忆，不会冒充作者明确要求
- 还没有按章节增量做梦，也没有多轮梦境历史比较

### 继续往前做的方向

1. 给梦境报告补“历史对比”，看当前报告和上一份报告里哪些慢线索在加强，哪些在消退
2. 把做梦候选拆成两类：
   - 可写回项目记忆
   - 只供 brainstorm/blueprint 参考
3. 后面如果再接调度，再考虑夜间自动做梦，不在这一版里直接上
