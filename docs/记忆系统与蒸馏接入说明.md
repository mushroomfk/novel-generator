# 记忆系统与蒸馏接入说明

本文记录项目记忆和结构化蒸馏的接入方式，核心能力有两部分：

1. 分层记忆
2. 结构化蒸馏

没有引入多用户画像、长期陪聊调度器或会话归档系统。当前项目是小说生成器，重点放在作品上下文、章节连续性和作者确认后的经验沉淀。

## 1. 当前已经接入的能力

### 项目记忆

- 项目记忆现在分成两层：
  - `manual_entries`
    作者手工维护，写明确规则、底线、偏好、阶段目标
  - `derived_entries`
    系统根据章节、架构文件、人物和世界要素自动整理
- 兼容索引仍保存在项目根目录下的 `project_memory.json`。
- 可读写正文已经拆到 `project_memory/` 目录，方便人工查看、编辑和版本管理。
- 旧格式 `entries` 会在读取时自动迁移，不需要手工处理历史项目。

### 文件型项目记忆

新的本地文件结构参考了 Claude Managed Agents Memory 的做法，但不依赖 Anthropic 服务。

```text
project_memory/
  author/
    canon/          作者写下的硬规则
    style/          作者偏好
    continuity/     作者指定的连续性要求
    warnings/       作者提醒不要写偏的内容
    planning/       作者指定的阶段目标
  system/
    canon/          系统整理的世界规则
    style/          系统整理的意象词场
    continuity/     系统整理的人物现状、当前推进、关键要素
    warnings/       系统整理的未解悬念
    planning/       系统整理的当前阶段目标
  audit.jsonl       每次记忆文件变化的审计记录
```

每条记忆是一份 markdown 文件，头部带 `id`、`title`、`category`、`source`、`updated_at`。后端读取项目详情时会优先读取这些 markdown 文件，再回到 `project_memory.json` 做兼容。这样直接改记忆文件，也会进入后续上下文。

手工记忆通过界面保存时，会更新 `project_memory/author/`。系统整理通过项目内容刷新时，会更新 `project_memory/system/`。后端写入或下次读取发现外部编辑时，会把文件新增、修改、删除记录到 `audit.jsonl`。

### 自动化策略

项目记忆现在不需要额外手工刷新。以下动作完成后，会自动刷新系统记忆，并把梦境候选写入 `project_memory/system/`：

- 保存章节正文
- 清空章节正文
- 保存设定文件
- 批量应用整书架构
- 导入参考资料
- 保存作者记忆
- 手动运行做梦整理

自动回流只写入 `system` 侧记忆，不会写进 `author` 侧。也就是说，模型或规则整理出来的东西只会被标成“系统整理”，不会冒充作者明确要求。

### 自动整理规则

系统会从现有项目内容里整理这些信息：

- 世界规则
- 主要人物现状
- 当前推进
- 关键要素
- 别丢的悬念
- 当前阶段目标
- 当前意象词场

这些内容是确定性整理，不依赖额外模型，读项目就能生成。

### 上下文注入

项目记忆已经进入这些链路：

- `build_project_context_bundle`
- 分步架构 `architecture_step`
- 章节工作流
- 继续扩写
- 蓝图生成
- brainstorming

进入提示词时会区分来源：

- `作者明确要求`
- `系统整理`

这样模型能分清哪些是作者硬要求，哪些是系统从项目里归纳出来的上下文。

### Obsidian 资料源

- Obsidian 作为可选资料源接入，不作为项目唯一数据源。
- 新建作品会自动创建项目内 `Vault/` 和常用目录，并写入默认同步配置；作者不用单独启用开关即可把长篇稳定档案作为项目资料源使用，外部 Vault 仍可在高级同步规则里替换。
- 配置保存在项目目录 `.gaoxia/obsidian.json`，上一次同步摘要保存在 `.gaoxia/obsidian_sync.json`。
- 同步会读取指定 Vault 下符合路径过滤的 Markdown 和 Canvas，解析 YAML frontmatter、正文内联属性、Dataview 段落内属性、`[[双链]]`、Markdown 内链、标签、别名、`type`、`status`、`usable_by_ai`、`summary / description / abstract / keywords / search_terms / 关键词` 等摘要 / 检索词 Properties、`summary:: / keywords::`、`[summary:: ...]`、`(keywords:: ...)`、`required_phrases / 必须出现` 和 `forbidden_phrases / 禁止出现`；frontmatter 字段名支持大小写、空格、连字符和下划线等常见属性写法，frontmatter 或正文内联属性里的 `source_notes / related_characters / related_notes / depends_on / foreshadows / payoffs / reveals / related_locations / related_props / related_organizations` 等关系字段会参与图谱解析，并把依赖、伏笔、兑现、揭示、相关地点等关系语义保留到 Obsidian 摘要、知识索引和章节上下文；章节上下文只显示目标章节可见的关系目标，摘要或正文里的未来双链、Markdown 内链和已知未来笔记纯文本标题会按章节安全内容隐藏。
- 路径过滤按大小写不敏感匹配；默认 `.obsidian/**`、`.trash/**` 和 `templates/**` 会同时排除 `.OBSIDIAN/`、`.Trash/`、`Templates/`，自定义 `drafts/**` 也会匹配 `Drafts/`，避免模板和草稿目录进入蒸馏与章节上下文；候选笔记超过 `max_notes` 时，会先按 Vault 相对路径稳定排序再应用数量上限，并在同步警告里提示有候选笔记未同步；候选总数和 `max_notes` 会进入来源签名，让界面的 skipped 和警告随 Vault 增删更新。
- AI 可见性字段和标签支持正向、反向写法：`usable_by_ai / ai_usable / AI可用 / 可供AI使用 / 可供模型使用 / 写作可用` 或 `#AI可用` 为真时视为可用；`no_ai / not_for_ai / exclude_from_ai / AI不可用 / 不供AI使用 / 不允许AI使用 / 勿用AI`、`#no-ai` 或 `#AI不可用` 为真时排除笔记；`no_ai: false` 或 `AI不可用: 否` 视为明确可用。Markdown frontmatter、正文内联属性、正文标签、HTML details 正文内联属性 / 标签和 Canvas 文本节点属性都按同一套规则判断；HTML details 正文声明不可用于 AI 或声明过滤状态时只排除该折叠块。
- 显式状态别名、布尔状态 Properties、状态标签和目录会参与过滤：`status: 正式设定 / official / final`、`canonical: true / published: yes`、正文或 Canvas 文本节点 `canonical:: true`、`#canonical / #正式 / #已发布` 或 `正式设定/`、`Published/` 等视为正式可用状态，`status: wip / archived`、`draft: true / private: true / archived: true`、正文或 Canvas 文本节点 `draft:: true`、`#draft / #草稿 / #private / #私密 / #废案` 或 `Drafts/`、`草稿/`、`Private/` 等视为过滤状态；显式 `status` 字段优先，不被布尔属性、标签或目录覆盖。
- YAML flow sequence 会按 Obsidian Properties 的常见写法处理：`aliases: ["潮师, 守账人"]`、`required_phrases: ["潮声异常, 不得提前解释"]` 会把引号里的逗号保留在同一项里；普通列表型 Properties 和正文内联属性里的 `keywords:: A, B`、`source_notes: 当前线索；未建笔记` 仍作为多值属性解析，支持逗号、顿号、半角分号和中文分号。
- YAML block scalar 会按 Obsidian Properties 的多行写法处理：`summary: >`、`description: |`、`summary: >2-`、`keywords: |2-` 会形成可检索摘要或列表字段内容；`keywords / source_notes / required_phrases` 等列表型字段用多行文本书写时，会按行进入检索词、图谱关系和写作约束；这些列表字段的单项写成 `- >` 或 `- |` 时，也会读取真实多行正文。
- YAML 对象列表和顶层嵌套对象会按 Obsidian 结构化 Properties 处理：章节计划、章节合同、剧情债务和人物弧线笔记里的 `scenes / required_beats / character_checks / debts_to_advance` 可以写成 `- goal: ...`、`conflict: ...`、`payoff: ...` 这类多字段对象，也可以写成单独 `-` 后换行维护对象字段，或用 `required_beats: [{goal: ..., evidence_sources: [{source_note: ...}]}]`、`- {goal: ..., payoff: ...}` 这类 YAML flow mapping；对象字段值可以用 `goal: >`、`reason: |` 这类 YAML block scalar 维护多行场景目标、理由或验收说明；对象里继续嵌套 `character_checks / evidence_sources` 等对象列表时也会递归解析，嵌套列表同样支持单独 `-` 后换行写对象字段。`chapter_contract:` 这类顶层对象里的 `chapter_range / objective / required_beats / acceptance_checks / evidence_sources` 等直接子字段也会进入章节范围、章节上下文和图谱关系。同步后会转成章节上下文可读的结构化行，对象里的双链和 Markdown 内链仍会进入链接、反向链接和图谱关系统计，并按目标章节隐藏未来笔记。
- 没有显式 `type / kind / 类型` 的笔记会按目录或标签推断类型。作者只把文件放在 `Characters/`、`Locations/`、`Plans/`、`Debts/`、`CharacterArcs/`、`Style/` 或 `XP/` 等目录，或只写 `#人物/主角`、正文 `#人物／主角`、`#章节计划/58`、`#剧情债务/伏笔` 这类层级标签时，同步摘要和蒸馏上下文仍能看到人物、地点、章节计划、剧情债务、人物弧线、文风规则或 XP 规则类型；显式 type 优先。Obsidian 多选 Properties 里的 `type: [主角, 人物]`、`type: [临时, 章节计划]` 会扫描整个列表并识别系统已知类型，完全未知的显式 type 会保留原值。
- 章节计划类层级标签会同时提供章节范围。`#章节计划/58`、`#章节合同/58-60`、`#场景卡/59`、`#scene-plan/59` 这类标签进入同步摘要、蒸馏材料和章节上下文时，会按标签里的章节过滤。
- 行尾 YAML 注释会被排除在字段值之外：`status: canonical # 正式设定`、`source_notes: [[当前线索]] # 来源说明`、列表项后的 `# 说明` 不会进入同步摘要、图谱关系或章节上下文；引号里的 `#` 和双链 heading 仍保留。
- `tags` / `tag` / `标签` 属性和正文标签会按 Obsidian 常见标签写法拆分，`tags: "#人物 #第58章 #剧透/57"`、`tags: #章节/44-45 #剧透/43`、多行 `tags: - #人物/配角`、`tags: 人物 主角`、`tags:: #支线 #第59章`、正文 `#人物／主角 #适用章节／40～42 #剧透／39` 会形成单个标签并参与类型推断、章节范围、剧透边界、检索预览和章节上下文；非标签字段里的 `#` 仍按行尾注释处理。
- `source_notes / related_characters / depends_on / foreshadows` 等关系字段支持 Markdown 内链，`[当前线索](Clues/当前线索.md)`、`[林追](../Characters/林追.md)` 和 `[林追](/Characters/林追.md)` 会按当前笔记路径、同目录相对路径或 Vault 根路径解析，并生成关系语义、可解析链接和反向链接；关系字段带 `#小节` 或 `^block` 时，小节 / 块引用会进入“关系小节”上下文和检索，图谱和反向链接仍按笔记文件记录，未来目标的小节名会按章节隐藏。
- 关系字段里的普通字符串和列表项按逗号拆分多值时，会保留 Markdown 内链标签、双链别名和目标路径内部的逗号；`source_notes: "[线索乙, 潮账](../Clues/线索乙.md)"`、`related_characters: ["[林追, 主角](../Characters/林追.md)"]` 和 `depends_on: "[[线索甲|账册, 初证]]"` 仍会生成关系语义、可解析链接和反向链接。
- Obsidian / Dataview 正文内联属性里的关系字段支持嵌套 Markdown 内链和双链别名逗号；`[source_notes:: [当前线索, 潮标](当前线索.md)]`、`(related_characters:: [林追, 主角](林追.md))` 和 `depends_on:: [[线索甲|账册, 初证]]` 仍会形成同步摘要、图谱关系和反向链接。
- 可见 callout 里的任务列表会参与同步摘要和蒸馏上下文：`> - [ ] status:: canonical`、`> - [!] source_notes:: [[当前线索]]`、`> - [?] required_phrases:: 潮声异常`，以及 `> ## 必须包含` 下的 `[>] / [/] / [-]` 等常见 Obsidian Tasks 状态任务项，会进入元数据、图谱关系、章节约束和章节安全摘要；隐藏 callout 里的同类内容仍会被排除。
- Markdown 表格会被转成章节上下文可读的结构化行。Markdown 笔记、Canvas 文本节点和可见 callout 中的章节合同、章节计划、剧情债务或人物弧线表格，如果包含 `章节目标 / 必须节拍 / 禁写动作 / 验收项 / 证据来源 / 相关人物` 等列，会进入知识索引、图谱关系、章节安全摘要、检索预览和证据正文；单元格里的 `\|` 会还原为普通 `|`；表格里的未来笔记标题、双链和路径仍按目标章节隐藏。
- Markdown 内链目标里的英文括号会作为文件名内容解析，`[林追旧档](../Characters/林追(旧).md)` 会指向 `Characters/林追(旧).md`，不会截断成不存在的 `林追(旧`；目标是未来笔记时仍会在章节安全摘要、检索预览和证据正文里隐藏。
- Markdown 内链目标里的转义字符和 title 会按链接语义处理，`[林追旧档](../Characters/林追\(旧\).md "旧档")` 会还原为 `Characters/林追(旧).md`，`[终局答案](../Secrets/未来真相 "终局")` 会去掉 title 后解析；目标是未来笔记时仍会在章节安全摘要、检索预览和证据正文里隐藏。
- Markdown 引用式链接会参与图谱解析，`[林追旧档][old]`、`[林追旧档]`、`[old]: ../Characters/林追\(旧\).md "旧档"` 和 `[林追旧档]: ../Characters/林追\(旧\).md "旧档"` 会生成关系语义、可解析链接和反向链接；引用定义指向未来笔记时，章节安全摘要、检索预览和证据正文会同时隐藏正文引用和定义行里的未来路径 / title；Markdown 脚注 `[^id]: ...`、缩进续行和正文脚注标记不进入知识图谱、检索预览、证据正文或章节上下文。
- HTML `<a href="...">` 链接会按 Markdown 内链参与图谱解析；目标是 Markdown 或 Canvas 笔记时生成可解析链接、反向链接和关系语义，目标是未来笔记时章节安全摘要、检索预览和证据正文会隐藏标签和路径，目标是本地附件时按附件过滤。
- Obsidian URI 链接会按 Vault 内部链接参与图谱解析；`obsidian://open?vault=Demo&file=Characters%2F林追.md` 和 `obsidian://advanced-uri?vault=Demo&filepath=Secrets%2F未来真相.md&heading=终局答案` 会解析为可定位笔记，`heading / header / section / block / blockid / block_id` 或 URI fragment 会进入小节 / 块引用上下文；关系字段、Markdown 链接、HTML `<a>` 链接和 Canvas link 节点里的 URI 指向未来笔记时，章节安全摘要、检索预览和证据正文会隐藏链接标签、路径和关系语义。
- Obsidian 相对路径双链会按来源笔记路径和路径段解析，`[[../Characters/林追]]`、`[[./当前线索]]`、`[[Clues/../Characters/林追]]`、`[[/Characters/林追]]` 会归一化为 Vault 内笔记路径，并生成关系语义、可解析链接和反向链接；如果目标笔记对当前章节不可见，章节安全摘要、检索预览和证据正文仍会隐藏未来标题与别名。
- Obsidian URL 编码双链会先解码再解析，`[[Characters/林%20追]]`、`[[../Secrets/未来%20真相]]` 会按解码后的 Vault 路径生成关系语义、可解析链接和反向链接；如果目标笔记对当前章节不可见，章节安全摘要、检索预览和证据正文仍会隐藏未来标题、路径与别名。
- Obsidian URL 编码保留字符会按路径内容处理，`[[Characters/林%23追]]` 和 `[线索](Secrets/未来%5E真相.md)` 不会被误拆成 heading、query 或 block 引用；章节安全摘要、检索预览和证据正文仍按解码后的真实目标过滤未来笔记。
- Obsidian 越出 Vault 的相对链接会被排除，根目录笔记里的 `[[../Outside/旧设定]]`、`[[Clues/../../Outside/旧设定]]`、`[[/../Outside/旧设定]]` 和 `[外部](/../Outside/旧设定.md)` 不会进入图谱链接、未解析链接或维护建议；子目录内回到 Vault 内部的相对路径仍会解析。
- Obsidian 块引用会按对应笔记进入知识索引和图谱。`[[当前线索^block-id]]`、`[[当前线索#小节^block-id]]` 不会被当成新的笔记标题；如果块引用指向未来笔记，章节安全摘要、检索预览和证据正文仍按目标章节隐藏。
- Obsidian 同笔记内部链接不进入跨笔记图谱。`[[当前线索#内部索引]]`、`[[当前线索^scene-a]]`、`[回看](当前线索.md#内部索引)` 这类目标仍是当前笔记的链接会从 links、resolved_links、backlinks 和 graph_relations 中排除，避免目录、heading 和 block 导航影响孤立笔记、反向链接和维护建议。

- 命中的 Obsidian 笔记如果带有必需 / 禁止短语，系统会额外生成“本章 Obsidian 写作约束”块，把 `必须包含` 和 `禁止出现` 分开列给写作模型。
- 连续性证据包会用同一类章节线索检索 `knowledge.db`，Obsidian 正式笔记可作为证据块进入承接简报；返回给生成和审校的证据正文会按目标章节重新生成图谱关系，并把正文里指向未来笔记的 `[[双链]]` 改写为“未开放设定”，把指向未来 Canvas 节点的边标签改写为“未开放关系”。如果图谱关系目标可见但关系标签写到未来笔记名，也会改写为“未开放设定”。章节化证据检索替换为安全内容后还会重新检查查询词，只命中未来标题、双链、Markdown 内链或已知未来笔记纯文本标签的候选不会进入证据包。
- 章节保存后的核验会增加 `Obsidian 设定` 维度：系统只检查目标章节可用的正式笔记；这些笔记里标记的禁止短语出现在正文时会记为高风险，即使正文没有提到笔记标题；正文提到该笔记、连续性证据命中该笔记，或少量连续章节范围明确绑定的笔记缺少必需短语时会记为警告。Obsidian 必写 / 禁写问题会计入必须修订问题，即使总分没有低于阈值，也能触发章节自动修订。Obsidian 核验签名按目标章节可见笔记计算，未来章节专用笔记变化不会让早期章节核验标记为过期。
- 任务蒸馏和 Agent 资料分析里的 Obsidian 资料也会按当前任务和目标章节筛选，避免无关笔记进入本章上下文；没有可用蒸馏摘要时，Agent 资料分析会按任务说明和目标章节选择 Obsidian 笔记，明确绑定当前章的笔记不会因为文件顺序靠后而被跳过；如果项目蒸馏摘要来自 Obsidian，章节任务会改用目标章节可见的资料摘要，资料摘要会携带可读“考据来源”，且不会保留指向未来笔记的正文双链或关系标题；章节任务前的 `review_knowledge` 会继承后续章节范围，整书架构前的资料分析保留全局资料视角。
- 叙事状态账本会把目标章节可见的 Obsidian 来源、必写项、禁写项和图谱风险并入章节任务卡；章节正文已经存在时，任务卡还会记录已满足必写项、未完成必写项和已触犯禁写项。未完成必写项和已触犯禁写项会转成高优先级叙事债务，进入后续章节的“必须处理或明确推进”提示；修订后如果正文满足必写项并避开禁写项，对应债务会标为已兑现。长篇稳定档案可用时，账本会把没有匹配到可用 Vault 笔记的剧情债务、人物弧线和图谱问题整理成维护建议，给出建议笔记路径、处理动作，以及带来源 ID、来源章节、相关人物字段、人物双链或来源笔记路径的 Markdown 草稿；剧情债务和人物草稿会按来源章节写入 `reveal_after_chapter`，多个来源章节时按最晚来源章开放，发布后按目标章节过滤，不会把后段自动维护笔记带入早期章节；账本还会生成维护摘要，统计待处理、高优先级、自动草稿、草稿缺失、Vault 笔记缺失、Vault 笔记已移动、Vault 待更新和已忽略数量，并把优先处理项提供给 Agent 规划上下文；Agent 路由 / 规划有目标章节时，会按目标章节可见维护项重新统计摘要并筛选建议明细，多章节指令会优先按生成、改稿、拆场或诊断的动作目标章节判断，没有明确目标章节的非架构任务只保留全局维护摘要，不暴露后段建议标题、路径或动作；重复出现的未解析双链会形成 `Graph/` 待审草稿并继承来源笔记的章节范围和剧透边界，来源章节范围不连续或多个开放式来源起点不同时会改用较晚可见的剧透边界，避免生成过宽章节范围，重名和歧义链接会形成修复提醒；已解析双链如果来源笔记可见范围没有被目标笔记可见范围覆盖，会形成章节范围不匹配风险；带未解析或歧义双链的笔记不会被计入孤立笔记；这些建议会出现在架构总览“稳定档案”页签和自学习面板，也会进入 Agent 规划上下文。Agent 路由 / 规划和自学习状态以维护刷新模式读取当前项目详情时，会用最新 Obsidian 摘要刷新这些建议，并可自动写入中高优先级待审草稿。中高优先级建议会在章节保存、Obsidian 同步或章节上下文生成时自动写入项目 `.gaoxia/obsidian_drafts/` 待审草稿，用户仍可显式保存、忽略、恢复或更新草稿；自动草稿未被人工改动时会随新增来源、来源内容和章节边界变化更新，人工改动过的草稿不会被自动覆盖，保存草稿遇到同路径既有人工内容时会保留原文；同一路径的维护建议即使 ID 变化也会沿用已有草稿状态，被忽略的同路径建议不会自动写草稿，也不会进入 Agent 优先处理项，恢复处理后会重新进入待处理和自动草稿流程；草稿文件被移动或删除时会显示草稿缺失并允许重新保存；发布过的 Vault 笔记被移动或改名后会先按内容签名识别，新生成的维护笔记带 `gaoxia_maintenance_id`，发布到 Vault 前也会恢复缺失的身份字段，内容被作者改过但身份唯一匹配时也会把维护记录改到新的 Vault 路径；如果对应维护项仍在列表中，面板会显示移动前后路径；没有唯一匹配或文件被删除时会显示 Vault 笔记缺失并允许重新发布，自动发布内容被判定落后时会显示 Vault 待更新，保存新版草稿会生成带正式 Vault 路径和系统建议路径的合并草稿；作者在 Obsidian 完成合并后可在面板单条或批量确认，系统记录当前 Vault 内容并刷新 Obsidian 摘要和知识库；架构总览“稳定档案”页签和自学习面板会显示维护摘要、自动草稿、人工改动草稿、保留人工草稿、草稿缺失、Vault 笔记缺失、Vault 笔记已移动、Vault 待更新、Vault 合并草稿、确认 Vault 已合并、已忽略和恢复处理入口；项目内 `Vault/` 会在章节保存、Obsidian 同步、章节上下文生成或稳定档案维护刷新后自动发布系统生成且未被人工改动的中高优先级维护项；普通读取项目详情不再触发 Vault 写入；项目目录外 Vault、人工改动草稿、合并项、缺失项和低优先级规则仍需要用户显式发布或确认。发布会检查目标路径在 Vault 内且不覆盖已有笔记，并重新同步 Obsidian 摘要和知识库，让新笔记进入图谱解析，Graph 新笔记会按继承的章节边界控制可见范围。模型叙事编辑生成下一章合同时，会读取当前章和下一章按章节过滤后的 Obsidian 约束、剧情债务和人物弧线。自学习状态接口读取章节任务卡时，会用当前项目详情刷新已有任务卡里的 Obsidian 约束和执行状态，避免 Vault 修改后面板继续展示旧要求。
- 架构总览“稳定档案”页签和自学习面板没有筛选时显示全局维护摘要；存在状态、来源章节或搜索筛选时，维护摘要按可见建议重新统计。从 Agent `obsidian_maintenance` 产物卡片进入指定章节维护队列后，摘要总数与列表显示数一致。
- 章节生成、改稿和诊断上下文会按目标章节把 Obsidian 待审草稿写入叙事状态块，作为资料维护提醒；这些提醒会按来源章节与目标章节的相关性排序，并显示来源章节；带章节范围或剧透边界的草稿（包括作者手工改动后的草稿文件）不会进入范围外章节提示，草稿 frontmatter 字段名支持大小写、空格、连字符和下划线等常见属性写法，提示会明确这些草稿不能当作 Vault 正式设定引用。每条提醒会读取对应真实草稿并校验维护 ID / 类型；`create_chapter_note` 草稿会额外显示“草稿预览”，从 frontmatter 或正文小节摘取 `chapter_summary / handoff_to_next / obsidian_required_missing`；`create_chapter_contract_note` 草稿会额外显示“合同预览”，从 Properties 或正文小节摘取章节目标、必须节拍、禁写动作和验收项；`create_style_rule_note` / `create_xp_rule_note` 草稿会额外显示“文风预览”或“XP预览”，从 Properties 或正文行摘取规则、适用范围、检查项、证据数和置信度；`create_story_*` 架构实体草稿会显示人物、地点、道具、组织、事件、技能或场景档案摘要；剧情债务和图谱等其它待审草稿只显示维护状态。
- 如果待审草稿文件缺失，章节生成、改稿和诊断上下文仍会按维护项里的 `source_chapters` / 正文“来源章节”判断可见范围；含后段来源的缺失草稿不会提前写入早期章节叙事状态块。
- 如果作者删除待审草稿 frontmatter，但正文仍保留 `source_chapters::` 或“来源章节：...”，章节生成、改稿和诊断上下文会按正文来源章节判断可见范围。
- 指向重复命名的链接不会被自动解析，模型上下文里会显示为歧义，避免把错误人物、组织或地点设定带入正文。章节安全内容会保留不涉及未来笔记的未解析双链和可见范围内的歧义双链；歧义名称如果同时命中后段不可见笔记，则不会在早期章节显示。
- `.gaoxia/obsidian_sync.json` 会记录来源签名；读取总览和写作上下文时会比对当前 Vault 文件签名，发现变化就刷新同步摘要。
- 系统不会自动写回项目目录外的独立 Obsidian Vault；默认项目内 `Vault/` 会在章节完成后自动发布系统生成且未被人工改动的中高优先级档案。外部 Vault、人工改动草稿、Vault 合并项、缺失项和低优先级规则仍需要用户在架构总览“稳定档案”页签或自学习面板显式发布或确认。章节保存后的剧情债务、人物弧线、章节合同和文风 / XP 学习仍由项目内 `.gaoxia/learning/` 文件维护；系统学习版文风 / XP 规则如果已变为 `active` 且没有匹配到 Vault 规则笔记，会生成 `Style/` 或 `XP/` 低优先级待审草稿，草稿带 `source_ids`，发布后才成为 Vault 正式规则。发布后的规则笔记如果保留 `source_ids`，作者改名、移动或重写规则表达后，系统仍会识别为同一条规则。

### 文风参考库蒸馏

- 每个文风方案会从作者参考库生成一段 `reference_distillate`
- 这段蒸馏不是替代原文片段，而是作为参考库的压缩说明
- 现在会同时进入：
  - `build_style_reference_text()`
  - 文风校准提示词 `_style_detail_prompt()`
  - 文风详情面板展示

蒸馏内容目前主要包括：

- 高频词场
- 句式和节奏参考
- 反复出现的意象或表达重心

### 系统学习版文风 / XP

- 章节正文保存后，`update_chapter_content_with_review_status()` 会根据最终正文和章节核验报告维护 `.gaoxia/learning/style_xp_evolution.json`。
- 记录内容包括句长、短句比例、段落长度、对白密度、章尾压力信号、文风核验结果和本次使用的 XP 预设。
- 同一条规则只在一个章节出现时保持 `observed`；出现在至少两个不同章节后变为 `active`。
- `build_prompt_support()` 在拿到 `project_id` 时会读取 `active` 规则，并在章节生成、润色、定稿、去 AI 和蓝图任务中加入“系统学习版文风 / XP”提示。
- `build_prompt_support()` 和 Agent 路由 / 规划上下文拿到目标章节时，还会读取目标章节可见的 Obsidian 文风 / XP 笔记。识别来源包括 `type: style_rule / xp_rule`、`Style/`、`XP/`、`文风/`、`写作规则/` 等路径，以及 `文风 / 风格规则 / XP / 写作经验` 等标签；只写 `style_rule / voice_rule / tone_rule / sentence_rhythm / imagery / dialogue_rule / avoid_style / examples / applies_to`，或 `xp_rule / precheck / postcheck / workflow / technique / avoid_xp` 等 Properties 的规则笔记，会通过同步后的结构化正文进入文风 / XP 提示，不受摘要或短预览长度影响；规则数量超过提示容量时，会按目标章节相关性优先保留本章专属规则，并在容量允许时保留文风和 XP 各自最相关条目；没有目标章节时也会读取同步记录中无章节边界的全局规则，并排除带章节范围或剧透边界的后段规则。
- 这份提示的优先级低于作者明确要求、手工文风和手工 XP；它不会改 `project_memory/author/`、文风方案、XP 预设或章节正文。
- Obsidian 文风 / XP 只作为提示来源，不写入 `.gaoxia/learning/style_xp_evolution.json`；章节范围和剧透边界按 Obsidian 同一套规则过滤，避免后段审美规则提前影响早期章节。系统学习版 `active` 规则会在缺少匹配 Vault 笔记时生成可审的 Obsidian 维护草稿，草稿记录来源规则、来源章节、剧透边界、`source_ids`、`style_rule` 或 `xp_rule` Properties，发布后再进入 Obsidian 文风 / XP 提示。发布后的规则笔记如果保留 `source_ids`，作者改名、移动或重写规则表达后，维护队列仍会识别为同一条系统学习规则。
- 规则整理不额外调用模型，章节核验不可用时也只记录正文特征和核验错误信息。

### 剧情债务与人物弧线

- 章节正文保存后，`record_project_narrative_state_observation()` 会维护 `.gaoxia/learning/narrative_state.json`。
- 这份状态包含剧情债务、人物弧线、章节任务卡、模型叙事审查、章节合同、合同执行回看、Obsidian 维护建议和维护摘要。
- 剧情债务会记录伏笔、承诺、关系变化和世界规则，字段包括来源章节、上次触碰章节、预计处理区间、状态、风险等级、证据和下一步处理要求。
- 人物弧线会记录主要人物当前阶段、上次出现章节、状态证据、未处理压力和后续检查项。
- 章节任务卡会按目标章节数判断当前章节阶段，例如开局立约、前段升级、中段转向、终局前加压、高潮准备和结局兑现，并给出本章任务、避免事项、下一章交接以及目标章节可见的 Obsidian 约束、剧情债务和人物弧线；章节已有正文时，还会标记 Obsidian 必写项的满足 / 缺失和禁写项触犯情况，并把缺失或触犯项写入后续可处理的叙事债务。自学习面板最新章节任务卡会展示这些 Obsidian 债务和人物弧线条目。账本会为未入 Vault 的中高风险债务、人物弧线和图谱问题生成人工可审的 Obsidian 笔记草稿，并用维护摘要标出待处理规模、缺失状态、已忽略数量和优先处理项；剧情债务草稿带 `source_ids`、`source_chapters`、`related_characters`、人物双链、按来源章节生成的 `reveal_after_chapter`，以及 `debt_content / debt_status / risk_level / next_required_action` Properties，预计处理区间写成 `expected_payoff_range` 而不是 `chapter_range`；人物状态草稿带来源 ID、来源章节、同样的剧透边界、`character / phase / current_state / unresolved_pressure / required_next_check` Properties 和 `人物状态` 标签；未解析双链草稿带 `aliases`、`source_notes`、来源章节范围和剧透边界，已解析但目标章节不可见的双链会形成范围修复建议；中高优先级草稿会在章节保存、Obsidian 同步或章节上下文生成时自动进入项目 `.gaoxia/obsidian_drafts/`，未人工改动的自动草稿会随新增来源、来源内容和章节边界变化更新，同一路径建议会沿用已有草稿状态，被忽略的同路径建议不会自动写草稿，恢复处理后会重新允许自动写草稿，草稿缺失时可重新保存，保存草稿不会覆盖同路径既有人工内容，项目内 `Vault/` 可由章节保存自动发布符合条件的系统草稿；项目目录外 Vault 和人工改动草稿仍由用户点击发布后进入 Obsidian 图谱解析；发布过的 Vault 笔记被移动或改名后会先按内容签名识别；新生成的维护笔记带 `gaoxia_maintenance_id`，发布到 Vault 前也会恢复缺失的身份字段，内容被作者改过但身份唯一匹配时维护建议也会改到新的 Vault 路径；剧情债务和人物状态笔记如果保留 `source_ids`，作者改名、移动或改写标题后仍会被识别为同一条账本来源；没有唯一匹配或文件被删除时，维护建议会提示可重新发布。
- 目标章节可见的 Obsidian 章节计划笔记会进入叙事状态账本提示和模型叙事编辑输入。系统会识别 `type: chapter_plan / scene_plan / chapter_contract`、`Plans/`、`Scenes/`、`章节计划/`、`场景卡/` 等路径，以及 `章节计划 / 章节大纲 / 场景卡 / 节拍表` 等标签；只有明确绑定目标章节或很窄章节范围的计划会进入当前章，后段计划不会出现在早期章节合同里。章节合同或场景卡只写 Properties 时，`objective / required_beats / debts_to_advance / debts_to_protect / character_checks / style_checks / forbidden_moves / acceptance_checks / evidence_sources / risk_notes` 会转成章节计划行。
- 章节计划、章节合同和场景卡标签可直接携带章节号，例如 `#章节计划/58`、`#章节合同/58-60`、`#场景卡/59`、`#scene-plan/59`；系统会把它们当作章节范围，不需要作者重复维护 `chapter_range`。
- 模型叙事编辑输出的下一章章节合同，如果没有匹配到目标章节可用的 Vault 计划或合同笔记，会生成 `Plans/` 中优先级待审草稿。草稿使用 `type: chapter_contract` 和目标章节 `chapter_range`，记录来源章节、合同目标、必须完成的节拍、债务推进、人物检查、文风检查、禁止动作、验收项和证据来源；发布到 Vault 前会作为非正式合同预览进入目标章节待审草稿提醒，发布到 Vault 后会作为正式章节计划进入目标章节提示，并停止显示同一合同的维护建议。发布后的合同笔记保留 `gaoxia_maintenance_id` 或 `source_ids` 时，作者改写正文后仍按同一合同识别。读取已发布 `chapter_contract` 时，系统按合同小节或 Properties 提取章节目标、节拍、债务、人物检查、文风检查、禁止动作、验收项、证据来源和风险提示，不按普通正文前几行截断；`evidence_sources` 会进入图谱关系。
- 目标章节可见的 Obsidian 剧情债务和人物弧线笔记会进入 Agent 路由 / 规划上下文、叙事状态账本和章节任务卡。系统会识别 `type: narrative_debt / plot_debt / character_arc / character_state`、`Debts/`、`PlotDebts/`、`CharacterArcs/`、`剧情债务/`、`人物弧线/` 等路径，以及 `剧情债务 / 叙事债务 / 人物弧线 / 人物状态` 等标签；章节生成前这些笔记会作为上下文约束，章节保存后会成为账本里的 `obsidian_debt` 或 `obsidian_arc` 来源，并显示在自学习面板最新章节任务卡里。剧情债务笔记只写 `debt_content / debt_status / risk_level / expected_payoff_range / next_required_action / related_characters`，或人物弧线笔记只写 `character / phase / current_state / unresolved_pressure / required_next_check` 时，这些 Properties 也会进入知识索引、账本状态、章节任务卡和模型叙事编辑输入；系统生成的同类维护草稿发布后也按这些结构化字段读取。模型叙事编辑生成下一章合同时，会读取下一章可见的这些结构化条目。
- Agent 能力上下文支持多个目标章节。路由 / 规划会识别“第 58 到 60 章”这类范围，也会在“先检查第一章，再生成第二章”中优先使用生成目标；包含“蓝图 / 架构”等词但明确写了章节范围时，也会优先按目标章节读取 Obsidian 任务；上下文最多展开前 3 个目标章节的 Obsidian 任务摘要，维护建议按这些目标章节共同筛选和排序；明确要求生成正文的 2 到 3 章范围会在计划阶段展开成逐章生成动作，每章再分别进入去 AI 和一致性复查；超过 3 章会提示分批或先整理章节蓝图；执行阶段跨到下一章时，会按新目标章刷新资料库和 Obsidian 分析摘要，并缓存给同章生成、改稿和复查使用。
- Agent 章节生成、draft 写回或改稿写回后，如果当前保存生成或更新了 Obsidian 维护草稿，执行结果会返回 `obsidian_maintenance` 产物，列出相关待审草稿、状态和路径；这些产物用于提示候选资料和打开维护队列；项目内 `Vault/` 的章节保存自动发布仍按后端条件执行，项目目录外 Vault 不自动发布。
- 待审草稿提示会读取项目 `.gaoxia/obsidian_drafts/` 中真实草稿文件的 frontmatter。作者在草稿里手工加入 `tags: [第58章起, 剧透/57]`、`tags: [Ch58+]`，或保留系统生成的多行 `tags:` 列表时，章节生成上下文会按正式 Obsidian 笔记相同的标签章节范围和剧透边界过滤这些草稿提醒。
- 草稿文件被移动或删除后，章节生成上下文会退回到维护项 `source_chapters` 可见性判断；第 59 章不会仅因建议路径存在而看到含第 60 章来源的缺失草稿。
- 草稿文件内容被作者改成无 frontmatter Markdown 时，章节生成上下文仍会扫描正文来源章节；第 59 章不会把正文标明含第 60 章来源的草稿当成全局维护项。章节档案草稿还会继续扫描正文里的章节摘要、下一章交接、未完成 Obsidian 必写项和章节正文摘录。
- 设置页保存了主模型 Key，或启用了第二审查模型时，章节保存后会执行模型版叙事审查。模型会接收当前章节、项目文档、旧账本、当前章节合同，以及当前章和下一章可见的 Obsidian 约束，输出带证据的债务更新、人物弧线变化、合同执行回看和下一章章节合同。没有证据的模型条目不会写入状态。
- `build_project_context_bundle()` 会把目标章节的叙事状态账本加入章节生成、改稿和诊断上下文。中后段章节会优先看到章节合同、必须处理、可轻触、不要提前揭开的剧情债务。
- 这份上下文也会按目标章节显示 Obsidian 待审草稿提醒，帮助后续生成知道哪些资料正在等待作者确认；带章节范围或剧透边界的草稿（包括作者手工改动后的草稿文件）不会进入范围外章节提示，草稿 frontmatter 字段名支持常见属性写法，也不会把草稿当正式设定。目标章节可见的 `create_chapter_note` 草稿会附带章节摘要、下一章交接和未完成必写项短预览，frontmatter 缺失时改读正文小节，让作者尚未发布章节档案时，后续章节仍能承接上一章；目标章节可见的 `create_chapter_contract_note` 草稿会附带合同目标、必须节拍、禁写动作和验收项短预览，让章节合同发布前也能进入目标章节的资料维护提醒。
- 这套机制不改章节正文，也不写入作者记忆；模型不可用时继续使用规则账本和章节任务卡。

### 项目蒸馏持久化

- `get_project_detail` 会返回当前可用的项目蒸馏报告；缺失或过期时可以即时生成用于展示和上下文组装。
- 详情读取本身不再写入新的 `project_distillation.json`。

- 写作回归报告会额外返回 `golden_evaluator_benchmark`，用模板腔、对白同质、连续性冲突和正常场景样本评估本地评审规则；还会返回 `humanize_ab_benchmark`，用固定小说片段做去 AI A/B，对比原文和预期改写后的评分、平均提升、正文长度比例和残留问题，并从真实章节生成 `project_sample_pool`，把项目样本池和蒸馏规则展示在自学习面板。
- 模型审查报告会额外返回 `humanize_model_judge` 和 `humanize_rule_update`。`humanize_model_judge` 会抽取项目样本池和历史 `chapter_humanize` 输出，让模型按自然度、人物声音、叙事张力、非模板化和误报风险评分；`humanize_rule_update` 会把模型认可的改法写入 `.gaoxia/learning/humanize_evolution_rules.json`，后续章节去 AI prompt 会读取这些项目规则。`humanize_review_patrol.json` 记录去 AI 智能巡检状态；章节正文保存、做梦完成和自学习心跳会按样本签名、项目规则、历史去 AI 输出分数和 12 小时冷却时间决定是否触发裁判。
- 章节低分核验和自动修订会生成额外的技能候选，用于沉淀“章节低分修订经验”。
- 这部分不会自动写入 `project_memory/author/`，也不会自动改章节正文。候选被作者标为已采纳后，会生成待确认草案；草案应用后才会写入作者侧项目记忆、创建或更新用户技能，或把调用规则标为作者采纳。
- Agent 的完整执行轨迹另存到应用数据目录下的 `logs/agent_trajectories.jsonl`，可以通过 `GET /api/studio/agent-trajectories` 查看。
- Agent 每次执行的 workflow 状态另存到项目目录 `.gaoxia/runs/{task_id}/`，包含预检、动作契约、心跳、产物校验和子任务状态文件。
- 技能库 `Agent 自学习` 面板可以查看能力看板、确认草案、候选、调用规则、系统学习版文风 / XP、剧情债务与人物弧线、模型叙事审查、章节合同、写作评价、写作回归、模型审查、失败案例、重复失败聚合、长期趋势、细分质量维度、技能统计、技能版本和技能包，也可以调整候选状态、触发技能库状态检查、保存排程、手动执行排程任务、回滚技能版本、导入导出技能包或把用户技能提升为全局技能。
- 多模型交叉审查默认不启用；设置页启用并填写完整配置，或配置 `NOVEL_REVIEW_MODEL_API_KEY`、`NOVEL_REVIEW_MODEL_BASE_URL`、`NOVEL_REVIEW_MODEL_NAME` 后，模型审查会增加第二审查模型结果。

### Agent 自学习状态

技能库的 `自我进化` / `Agent 自学习` 面板默认读取 `GET /api/projects/{project_id}/self-evolution`。`GET /api/studio/self-evolution?project_id=...` 保留为兼容入口，返回同一套项目自学习状态。状态会汇总：

- `.gaoxia/learning/reviews.jsonl` 里的记忆候选和技能候选
- `logs/agent_trajectories.jsonl` 里的失败执行样本
- 章节产物 metadata 里的核验低分、风险状态和自动修订记录
- `logs/prompt_history.jsonl` 里的模型调用失败记录
- `skills/` 和 `.skill_usage.json` 里的技能使用状态

候选、草案和调用规则都需要作者确认后才会写入作者记忆、创建或更新用户技能，或进入后续 Agent 规划上下文。`GET /api/studio/skills/curation` 继续提供技能整理报告。

## 2. 为什么这样接

- 小说项目最容易爆的是上下文长度，不是用户画像。
- 对章节生成真正有价值的是“近期推进、人物现状、别丢的悬念、当前阶段目标”这类项目态信息。
- 文风部分真正值得蒸馏的是“作者参考库里的共性写法”，不是泛化的用户画像。

当前接法保留对小说写作最有价值的部分，同时避开对项目帮助不大的重型模块。

- `项目记忆` 面板拆成两块：
  - `作者明确要求`

- Agent 写回章节正文时会默认串起正文生成、小说专用去 AI 改稿和一致性复查；去 AI 会保留剧情事实和人物声音，处理模板腔、套版画面、抽象情绪、潜台词解释、对白同质化和节奏过匀，完整章节修订稿明显短于原文时会拒绝本次结果；章节工作流里的 draft 写回和单独改稿也会进入同一套复查链路。章节写回后触发系统记忆刷新，章节核验报告会作为产物进入消息区，方便作者决定是否继续改。

## 6. 做梦机制

### 接入方式

- 项目根目录新增 `project_dreams.json`
- 每次“做梦”都会产出一份上一次梦境报告，结构包括：
  - `summary`
  - `themes`
  - `insights`
  - `open_questions`
  - `memory_candidates`
- 这份报告不会自动改正文。
- 候选会自动写入系统侧项目记忆，不再需要手工点选。

### 为什么这样接

- 做梦机制更像慢路径整理和受控回流，不是自动续写。
- 小说项目最怕的是“梦境结果直接污染正文”。
- 所以目前只把梦境结果接给规划类能力：
  - `brainstorm`
  - `blueprint`
  - `continue-project`
  - `architecture-step`

正文生成、章节续写、改稿都不吃梦境摘要。

### 结果怎么产生

- 有可用模型时：
  - 走模型版做梦，输出结构化 JSON 报告
- 没配模型，或者模型调用失败时：
  - 自动回退到规则版做梦
  - 依然会根据当前推进、悬念、人物现状和阶段目标生成一份可读报告

### 过期规则

- 梦境报告会记录自己的 `source_signature`
- 只要章节正文或项目设定文件变了，旧梦境就会被标记为 `is_stale`
- 过期后的梦境结果：
  - 不再进入规划类提示词
  - 仍然可以展示给作者看
  - 但建议先重跑一轮

### 前端入口

- `Story Overview -> 梦境整理`
- 这里可以：
  - 手动触发一轮做梦
  - 查看上一次梦境摘要、慢线索判断、待验证问题
  - 把某条候选写回项目记忆

### 当前边界

- 现在还是手动触发，不是定时调度
- 梦境候选默认写入 `system` 侧项目记忆，不会冒充作者明确要求
- 还没有按章节增量做梦，也没有多轮梦境历史比较

### 继续往前做的方向

1. 给梦境报告补“历史对比”，看当前报告和上一份报告里哪些慢线索在加强，哪些在消退
2. 把做梦候选拆成两类：
   - 可写回项目记忆
   - 只供 brainstorm/blueprint 参考
3. 后面如果再接调度，再考虑夜间自动做梦，不在这一版里直接上
