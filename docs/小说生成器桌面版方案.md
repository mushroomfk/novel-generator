# 稿匣桌面版方案

## Summary

- 以独立桌面写作工作台为产品目标，不复用外部仓库代码、Prompt 文本或实现细节。
- 技术栈定为 `Tauri 2 + Vue 3 + TypeScript + Python 3.12 sidecar`。Tauri 官方支持把外部二进制作为 sidecar 打包，适合把 Python 服务内置到桌面应用中；Python sidecar 按平台分别打包，优先评估 Nuitka（体积更小、启动更快），PyInstaller 作为备选。
- 首发目标是 `Windows + macOS` 本地安装版，`纯本地存储`，`云模型 only`，`本地激活码`，`手动下载安装更新`。
- 功能范围按完整桌面写作工作台推进，但首发明确排除：WebDAV/云同步、账号系统、自动更新、Ollama/本地模型。

参考链接：

- [Tauri Sidecar](https://tauri.app/develop/sidecar/)
- [Tauri Distribute](https://v2.tauri.app/distribute/)
- [Nuitka Docs](https://nuitka.net/doc/user-manual.html)
- [PyInstaller Docs](https://pyinstaller.org/en/stable/)

## Key Changes

### 1. 产品与架构

- 新建一个桌面工程，按当前产品目标独立实现。
- 前端保留”多页面工作台”产品形态，但桌面壳负责：
  - 启动/关闭本地 Python 服务
  - 选择项目目录
  - 打开日志目录
  - 导入激活码
  - 健康检查与异常恢复
- Python sidecar 只提供本机 `127.0.0.1` 服务，不对局域网暴露。
- 后端 Web 框架选用 **FastAPI + Uvicorn**：原生异步、SSE 支持好、OpenAPI 文档自动生成。

### 2. 后端能力边界

- 独立设计本地 API，保留清晰的资源划分：
  - `/api/projects`
  - `/api/config`
  - `/api/generate/*`
  - `/api/styles`
  - `/api/knowledge`
  - `/api/projects/{project_id}/research/historical`
  - `/api/brainstorm`
  - `/api/consistency`
  - `/api/files`
  - `/api/logs`
  - `/api/license`
- 长任务统一走 SSE，事件协议固定为：
  - `started` — 任务已接受，返回 task_id
  - `progress` — 进度更新，含 step/total/message 字段
  - `chunk` — 流式文本片段（用于章节生成的逐字输出）
  - `result` — 最终结果
  - `error` — 错误信息，含 code/message
  - `done` — 流结束信号
- 后端内部不再挂靠旧的 `web_server.py` 风格单体类，而是拆成服务层：
  - `project_service` — 项目 CRUD、项目索引维护
  - `model_service` — LLM/Embedding 适配器管理、调用封装、重试与清洗
  - `generation_service` — 核心生成管线编排（架构→蓝图→章节→定稿）
  - `context_service` — 上下文组装与压缩（摘要、角色状态、知识检索）
  - `style_service` — 文风分析、叙事DNA、预设管理
  - `knowledge_service` — 知识库导入、分段、检索
  - `license_service` — 许可证校验、设备指纹

### 3. 功能实现范围

- 首发包含这些主能力：
  - 项目管理
  - 模型配置
  - 架构生成
  - 目录生成
  - 章节生成
  - 定稿/润色
  - 去 AI 痕迹
  - 创意讨论
  - 文风模板
  - 叙事 DNA
  - 作者参考库/知识库
  - 国内联网考据
  - 一致性检查
  - 阅读器
  - 导出整本小说
  - 运行日志
- 首发不做这些能力：
  - WebDAV
  - 云同步
  - 账号登录
  - 自动更新
  - 本地大模型推理
- 云模型首发统一采用”OpenAI 兼容接口”抽象；Gemini 等非标准接口如果需要，放在适配层，不进入 UI 特判逻辑。

### 4. 核心生成管线

本节描述产品核心——小说生成管线的技术方案。所有 Prompt 模板独立编写，不复用上游文本。

#### 4.1 管线总览：6 步流水线

```
Step 1: 架构生成（architecture）
  ├── 1a. 核心种子 — 一句话概括故事本质
  ├── 1b. 角色设定 — 每个角色的驱动力、语言画像、弧线
  ├── 1c. 世界观 — 物理/社会/隐喻三维度
  └── 1d. 情节骨架 — 三幕式结构 + 转折点

Step 2: 蓝图生成（blueprint）
  └── 分块生成章节目录，每章含：标题、核心事件、悬念设计、涉及角色

Step 3: 章节生成（chapter）
  └── 逐章生成正文，注入多源上下文（见 4.2 节）

Step 4: 定稿（finalization）
  ├── 更新前文滚动摘要
  ├── 分角色更新状态
  └── 更新知识库索引

Step 5: 去 AI 痕迹（humanize）
  └── 分轮分深度处理（见 4.5 节）

Step 6: 续写扩展（continue）
  └── 在已有架构上追加新剧情弧、新角色，回到 Step 2
```

**断点续作机制**：每个步骤完成后将阶段性成果写入 `checkpoint.json`，中断后可从最近断点恢复，无需重跑整条管线。

**分步 vs 一键**：支持两种模式。分步模式允许用户在每个步骤后审阅、手动编辑、基于修改建议修订，然后再进入下一步。一键模式自动走完全部流程。

#### 4.2 上下文管理策略（关键设计）

长篇小说（20-50万字）远超模型上下文窗口，需要多层策略保证生成质量和一致性：

```
生成第 N 章时，注入以下上下文（按优先级排列）：

[必选]
1. 小说架构（核心种子 + 世界观 + 情节骨架）    ~2000 字
2. 当前章 + 下一章蓝图元数据                    ~500 字
3. 前文滚动摘要（global_summary）               ~1500 字
4. 当前章涉及角色的状态                         ~800 字（按角色过滤，非全量）
5. 前一章末尾 800 字                            ~800 字

[按需]
6. 最近 3 章的针对性摘要（由 LLM 生成）           ~800 字
7. 知识库/作者参考库检索结果                      ~2000 字
8. 文风指令 + 叙事 DNA 指令                      ~500 字
9. 世界观补充注入                                ~500 字
```

**Token 预算控制**：上下文总量控制在 8K-12K 字（约 15K-22K tokens），为生成内容预留充足空间。每个组件设硬上限，超出时触发压缩。

**滚动摘要**：每章定稿后调用 LLM 将章节内容”压入”全局摘要。摘要不是简单追加，而是”滚动更新”——新章节信息融入已有摘要，淘汰远期细节，保留关键伏笔和人物关系变化。

**角色状态跟踪**：以树状结构记录每个角色的属性/状态/关系/事件。定稿后只对本章出场角色执行分角色独立更新（而非整体更新），减少单次 prompt 大小和出错概率。

**上下文压缩**：当摘要或角色状态积累超过阈值（摘要 > 3000字，角色状态 > 4000字）时，调用专门的压缩 Prompt 进行语义压缩，压缩前自动备份原文。

#### 4.3 知识库技术方案

采用 **SQLite FTS5 全文检索**（不引入 ChromaDB/向量数据库），理由：
- 桌面应用不应引入 torch/sentence-transformers 等重依赖（仅这些就 2GB+）
- FTS5 原生支持中文分词（配合 jieba 分词器），查询性能优异
- SQLite 随项目目录移动，零配置，符合”目录即项目”原则
- 对于本应用场景（作者参考文本检索），关键词匹配比语义检索更可控

**导入流程**：
1. 读取 .txt/.md 文件（多编码尝试：utf-8 → gbk → gb18030 → big5）
2. 中文感知分段：按段落/标点分句，合并为 300-500 字的文档块
3. 用 jieba 对每个块做分词，存入 FTS5 索引

**检索流程**（两阶段）：
1. LLM 根据当前章蓝图生成 3-5 组检索关键词
2. FTS5 执行关键词检索，返回 top-K 相关片段
3. （可选）LLM 对检索结果做相关性过滤，去除噪声

**作者参考库**：独立于通用知识库，采用混合策略——关键词检索取最相关片段 + 随机采样取多样性片段，合并后限制 2000 字。

**v2 可选升级路径**：如果用户反馈语义检索效果不足，后续可引入轻量 Embedding（如调用云端 Embedding API），将 FTS5 升级为混合检索，不需要本地跑模型。

#### 4.4 Prompt 工程架构

**三层管理**：
1. **内置默认** — Python 代码中硬编码的基础模板
2. **预设方案** — JSON 文件存储的预设（如”网络小说”、”严肃文学”、”短篇小说”），可覆盖默认值
3. **用户自定义** — 用户在 UI 中编辑后保存的个人模板

加载优先级：用户自定义 > 预设方案 > 内置默认。

**核心 Prompt 清单**（需独立编写，不复用上游）：

| 阶段 | Prompt | 作用 |
|------|--------|------|
| 架构 | `core_seed` | 从主题/类型/章数/字数提炼故事核心公式 |
| 架构 | `character_design` | 角色设定：驱动力、语言画像、弧线、关系网 |
| 架构 | `world_building` | 世界观构建：物理/社会/隐喻三维度 |
| 架构 | `plot_structure` | 情节骨架：三幕式 + 转折点设计 |
| 蓝图 | `chapter_blueprint` | 章节目录：事件流、悬念节奏、伏笔操作 |
| 章节 | `first_chapter_draft` | 首章生成（注入完整架构） |
| 章节 | `next_chapter_draft` | 后续章生成（注入摘要+状态+前章） |
| 定稿 | `update_summary` | 将新章内容融入滚动摘要 |
| 定稿 | `update_character_state` | 分角色更新状态 |
| 去AI | `humanize_*` | 分轮去AI痕迹（见 4.5 节） |
| 压缩 | `compress_summary` | 摘要超长时的语义压缩 |
| 压缩 | `compress_character_state` | 角色状态超长时的语义压缩 |
| 检索 | `generate_search_keywords` | 为知识库检索生成关键词 |
| 检索 | `filter_search_results` | 对检索结果做相关性过滤 |
| 摘要 | `summarize_recent_chapters` | 面向当前写作需求的近章精准摘要 |
| 文风 | `style_analysis` | 分析样本文本提取文风特征 |
| DNA | `narrative_dna_analysis` | 分析样本提取叙事结构模式 |
| 讨论 | `brainstorm` | 带项目上下文的创意讨论 |
| 一致性 | `consistency_check` | 跨章节一致性检查 |

#### 4.5 去 AI 痕迹方案

分三种深度，用户可选：

- **快速（quick）**：单轮处理，一次性应用全部规则
- **标准（standard）**：两轮处理——句式排版 → AI 高频词汇替换
- **深度（deep）**：三轮处理——句式排版 → AI 词汇替换 → 节奏与结构重塑

每轮处理时注入前章末尾 200 字 + 后章开头 200 字，确保修改不破坏章节间过渡衔接。

返回格式：修改后全文 + 修改清单（方便前端做 diff 对比展示）。

支持批量处理（选中多章一键去痕迹）。

#### 4.6 文风与叙事 DNA

**文风（Style）** — 文笔层面：词汇倾向、句式特征、修辞手法、节奏感。
- 分析：用户上传样本文本 → LLM 提取文风特征 → 保存为模板 JSON
- 应用：生成章节时注入文风指令前缀

**叙事 DNA** — 叙事层面：内容配比（对话/描写/心理/动作）、推进节奏、场景结构。
- 分析：用户上传样本文本 → LLM 提取叙事模式 → 保存为模板 JSON
- 应用：可注入架构/蓝图/章节三个层级

两者独立管理，可单独或叠加使用。

### 5. 模型适配层

#### 5.1 LLM 适配器

采用 `BaseLLMAdapter` 基类 + 具体适配器模式。首发支持：

| 适配器 | 接口协议 | 流式支持 | 说明 |
|--------|---------|---------|------|
| `OpenAICompatibleAdapter` | OpenAI Chat Completions | ✅ | 通用适配器，覆盖 DeepSeek/硅基流动/Grok/Moonshot 等 |
| `OpenAIAdapter` | OpenAI 原生 | ✅ | 支持 thinking 模式（reasoning_content 字段） |
| `VolcanoEngineAdapter` | 火山引擎 | ✅ | 豆包/方舟模型 |

**设计原则**：OpenAI 兼容接口是主线，只有协议确实不兼容时才新增适配器。UI 不做适配器特判。

**统一调用入口**：`invoke_with_retry()`
- 最多 3 次指数退避重试
- 自动清洗输出中的 ``` 标记和 `<think>` 标签
- 流式中断时保留已生成的部分内容（附加 `[PARTIAL]` 标记）
- 每次调用记录到 `prompt_history.jsonl`（含 pending/done/error/partial 状态）
- 中文 token 估算：约 1.8 token/字符

#### 5.2 Embedding 适配层（v1 可选）

v1 知识库采用 FTS5，不强制依赖 Embedding。但预留接口：
- 如果用户配置了 Embedding API（如 OpenAI text-embedding-3-small），自动升级为混合检索
- 适配器复用 LLM 的 base_url/api_key 配置，零额外配置成本

### 6. 本地数据与授权

#### 6.1 数据目录结构

应用数据目录固定为用户目录下的 app data 路径：
- Windows: `%APPDATA%/NovelGenerator/`
- macOS: `~/Library/Application Support/NovelGenerator/`

```
NovelGenerator/
  app_config.json                    -- 全局配置（模型设置等）
  license.json                       -- 许可证信息
  projects/
    index.json                       -- 项目索引（id, name, path, updatedAt）
  logs/
    app.log                          -- 运行日志（按日轮转，保留 7 天）
    prompt_history.jsonl             -- LLM 调用历史（JSON Lines）
  prompts/
    网络小说.json                     -- 预设 Prompt 方案
    严肃文学.json
  styles/
    <style-id>.json                  -- 文风模板
  cache/                             -- 临时缓存
```

#### 6.2 项目目录结构

```
<project-dir>/
  project.json                       -- 项目元数据（id, name, 类型, 章数, 字数目标, 创建时间）
  core_seed.txt                      -- 核心种子
  character_design.txt               -- 角色设定
  character_state.txt                -- 角色状态（每章定稿后更新）
  world_building.txt                 -- 世界观
  plot_structure.txt                 -- 情节骨架
  blueprint.txt                      -- 章节蓝图/目录
  global_summary.txt                 -- 前文滚动摘要
  checkpoint.json                    -- 生成断点信息
  chapters/
    chapter_001.txt                  -- 各章正文
    chapter_002.txt
    ...
  knowledge.db                       -- SQLite FTS5 知识库
  backups/                           -- 压缩前的自动备份
```

#### 6.3 数据安全

- **原子写入**：所有 JSON/文本写入先写临时文件（`.tmp`后缀），成功后 `rename` 替换原文件，防止写入中断导致数据损坏。
- **API Key 存储**：使用系统密钥链（macOS Keychain / Windows Credential Manager），通过 Tauri IPC 调用 Rust 层的 `keyring` crate 实现。不在 JSON 文件中存储明文密钥。
- **自动备份**：摘要/角色状态压缩前自动备份原文到 `backups/` 目录。

#### 6.4 激活方案

- 采用本地签名许可证：
  - 应用内导入激活码/许可证文件
  - 本地校验 Ed25519 公钥签名
  - 不依赖持续在线
  - 绑定设备指纹（取 CPU ID + 磁盘序列号的哈希）和授权到期时间
- **设备指纹容错**：绑定时记录 3 个硬件特征，满足其中 2 个即视为同一设备，兼容用户更换单个硬件的场景。
- 授权校验失败时，阻止进入生成能力，但允许查看已有项目和导出本地文本。

### 7. 前端与桌面交互

- UI 采用中文优先，预留 i18n 键值结构（但 v1 不做多语言翻译）。
- Vue 前端只调用本地 API 和少量桌面 IPC，不直接操作文件系统。
- 需要新增的桌面 IPC 接口：
  - `selectProjectDirectory` — 打开系统目录选择对话框
  - `revealInFinderOrExplorer` — 在文件管理器中显示目录
  - `importLicenseFile` — 打开文件选择对话框导入许可证
  - `getAppVersion` — 获取应用版本号
  - `getBackendStatus` — 获取 Python sidecar 运行状态
  - `collectDiagnostics` — 收集诊断信息（版本、日志、配置快照）
  - `storeCredential` / `getCredential` — API Key 安全存取（调用系统密钥链）
- 页面结构沿用上游信息架构，但组件和样式独立实现，避免代码和视觉直接复制。

### 8. Sidecar 进程管理

#### 8.1 打包方案选择

| 方案 | 产物体积 | 冷启动时间 | macOS 公证 | 推荐度 |
|------|---------|-----------|-----------|-------|
| Nuitka (--standalone) | 40-80MB | 1-3秒 | 较友好 | ⭐ 首选 |
| PyInstaller (--onedir) | 80-150MB | 3-8秒 | 问题较多 | 备选 |
| PyInstaller (--onefile) | 80-150MB | 5-15秒 | 问题较多 | ❌ 不推荐 |

**决策**：优先用 Nuitka `--standalone` 模式，如果遇到兼容性问题再回退 PyInstaller `--onedir`。需要在项目初期做 PoC 验证。

**依赖精简**：v1 不引入 torch/transformers/sentence-transformers（知识库用 FTS5 代替向量检索），Python 依赖控制在 FastAPI + httpx + jieba + 标准库范围，预估打包体积 30-50MB。

#### 8.2 进程生命周期

```
Tauri 启动
  │
  ├── 调用 shell().sidecar(“novel-backend”).spawn()
  │     ├── 传入参数：--port <随机端口> --data-dir <数据目录>
  │     └── 监听 stdout/stderr 事件流
  │
  ├── 健康检查循环（每 500ms 轮询 /api/app/health）
  │     ├── 最多等待 15 秒
  │     ├── 成功 → 前端解除 loading 遮罩
  │     └── 超时 → 显示错误对话框，提供”重试”和”查看日志”
  │
  ├── 运行中监控（每 30s 心跳检查）
  │     └── 连续 3 次失败 → 自动重启 sidecar，前端显示”服务重连中”
  │
  └── Tauri 退出
        ├── 发送 POST /api/app/shutdown（优雅关闭，等待进行中的任务完成）
        ├── 等待 5 秒
        └── 如果进程仍在 → kill()
```

**端口分配**：不固定端口，启动时随机选择可用端口，通过启动参数传入。避免多实例端口冲突。

#### 8.3 生成任务中断恢复

- 每章生成完成后立即写入 `chapters/chapter_NNN.txt` + 更新 `checkpoint.json`
- sidecar 崩溃时，已完成的章节不丢失，只需从 checkpoint 记录的下一章继续
- 流式生成中断时（partial 结果），保存已生成的部分文本并标记为”未完成”，用户可选择从断点续写或重新生成该章

### 9. 性能预算与成本估算

#### 9.1 单章生成 Token 消耗

| 步骤 | 输入 tokens | 输出 tokens | 说明 |
|------|-----------|-----------|------|
| 章节生成 | ~15K | ~5K | 主要成本 |
| 摘要更新 | ~8K | ~2K | 章节内容 + 旧摘要 |
| 角色状态更新 | ~3K × N角色 | ~1K × N | 分角色独立调用 |
| 检索关键词生成 | ~2K | ~0.5K | 可选 |
| 合计（2角色） | ~31K | ~9.5K | 约 40.5K tokens/章 |

#### 9.2 整本小说成本估算

以 200 章（约 40 万字）小说为例：
- 架构生成：~100K tokens（一次性）
- 蓝图生成：~200K tokens（一次性）
- 章节生成+定稿：~40K × 200 = 8M tokens
- 去 AI 痕迹（standard）：~15K × 200 = 3M tokens
- **总计约 11.3M tokens**

以 DeepSeek V3 计价（输入 ¥1/M tokens，输出 ¥2/M tokens）：
- 总成本约 **¥20-30/本**

以 GPT-4o 计价（输入 $2.5/M，输出 $10/M）：
- 总成本约 **$100-120/本**

**前端需展示实时 Token 消耗统计，帮助用户掌控成本。**

## Assumptions

- 本方案只记录当前产品需求和实现边界，不做外部源码级继承。
- v1 不做自动更新；版本升级靠手动下载新安装包。但前端启动时检查 GitHub Release 版本号，有新版本时提示用户。
- v1 不做账号系统；商业化先靠本地激活码。
- v1 不做云同步；项目完全保存在本机。
- v1 不做 Ollama 和本地模型；只接云模型。
- v1 不是”浏览器应用套壳”，而是”桌面壳 + 本地服务”的正式桌面软件。
- v1 Python 依赖精简，不引入 torch/transformers 等重型 ML 库；知识库检索用 FTS5 实现。

## Risks & Mitigations

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Nuitka 打包兼容性问题 | 阻塞发布 | PoC 先行验证；PyInstaller --onedir 作为 Plan B |
| macOS 公证被拒 | macOS 无法分发 | 提前研究 notarytool 流程；预留 Developer ID 签名 |
| Prompt 生成质量不达标 | 产品核心价值受损 | PoC 阶段集中迭代 Prompt；支持用户自定义 Prompt 作为兜底 |
| 长篇小说上下文退化 | 后期章节质量下降 | 多层上下文策略 + 压缩机制；支持用户手动编辑摘要/状态 |
| Token 成本超出用户预期 | 用户流失 | 前端实时展示消耗；支持选择不同价位模型；批量操作前预估成本 |
| FTS5 检索效果不如向量检索 | 知识库功能鸡肋 | 预留云端 Embedding 升级路径；先用 PoC 验证效果 |
