# 核心引擎说明

本文记录当前核心引擎的十条主线：

1. `Embedding / RAG`
2. `分步架构引擎`
3. `文风 DNA 校准`
4. `章节续写候选与审校`
5. `批量生成任务队列`
6. `故事总览抽取`
7. `Agent 执行状态与动作契约`
8. `自我进化报告与技能维护`
9. `旧稿接管导入`
10. `项目迁移包`

这些能力都已经接进当前界面，不额外开新页面，入口都在现有的技能区和设置区。

## 1. Embedding / RAG

### 现在的结构

- 写作模型和 Embedding 模型在后端配置中分开保存；设置页不再显示 Embedding 配置入口，面向普通作者固定使用随 sidecar 打包的本地 `BAAI/bge-small-zh-v1.5`。
- 设置面板现在会同时保存两组配置：
  - `model`：章节生成、蓝图、架构、文风分析这些文本生成任务
  - `embedding`：知识切片的索引和查询向量
- 后端配置文件现在是统一的 `AppConfig`，内部包含 `model` 和 `embedding` 两块。
- 后端收到旧的单独 `ModelConfig` 保存请求时会保留现有 Embedding；没有现有配置时使用本地默认值。收到完整 `AppConfigUpdateRequest` 时仍会保留传入的 `embedding`，用于旧配置兼容和直接 API 调用。

### 索引方式

- 项目创建后，后端会把这些内容纳入知识索引：
  - 架构文件
  - 章节正文
  - 用户导入的资料
  - 已启用的 Obsidian Vault 笔记
- 知识库底层现在分成三层：
  - `knowledge_chunks`：原始切片
  - `knowledge_chunks_fts`：SQLite FTS 关键词检索
  - `knowledge_vectors`：二进制向量、维度和范数
- 每次重建索引时，后端会记录：
  - `source_signature`
  - `embedding_signature`
- 章节、设定文件、导入资料发生变化时，会按 `source_key` 刷新对应来源的切片和向量；Obsidian 笔记使用 `obsidian:<relative_path>` 作为来源键。
- 只有目标章节数、schema、来源签名或 Embedding 配置发生整体变化时，才会重建完整索引。
- 旧版 `vector_json` 行会在初始化知识库时迁移到二进制向量列。
- 内置本地 Embedding 由 `fastembed` + ONNX Runtime 直接加载，模型文件在 `novel_backend/assets/embedding_models/fast-bge-small-zh-v1.5`，维度为 512；运行时只读取打包内文件，不依赖 HuggingFace 或其它外部下载。

### 查询方式

- `search_project_knowledge()` 现在是混合检索：
  - 先用 FTS 取候选；中文查询会优先使用较长片段，并按查询片段和候选正文的重合度加权，避免长句检索只命中开头单字
  - 再只对候选做语义相似度计算
  - 阿里百炼配置可额外调用 `qwen3-rerank` 官方 OpenAI 兼容端点 `/compatible-api/v1/reranks`
  - 最后合并排序
- 返回结果会带 `match_type`：
  - `keyword`
  - `semantic`
  - `hybrid`
  - `rerank`
- 返回前会按来源做混合，避免单一来源占满请求数量；章节正文、资料库和 Obsidian 命中都有机会保留在结果里。

### 目前支持

- 内置本地 `local-fastembed`：`BAAI/bge-small-zh-v1.5`，512 维，中文，随 sidecar 打包
- OpenAI-compatible `/embeddings` 仍保留在后端配置兼容路径里，设置页不提供入口
- OpenAI-compatible `chat/completions` 用于写作模型和第二审查模型；传输层会移除 `temperature / top_p` 这类可选采样参数，并对 SSL EOF、DNS 解析失败、远端中途断开、临时连接错误和可重试 5xx / 429 默认最多重试 5 次，等待间隔可用 `NOVEL_MODEL_RETRY_DELAYS` 调整
- 阿里百炼 `qwen3-rerank` 官方 OpenAI 兼容 `/compatible-api/v1/reranks`
- 后端配置仍支持 `base_url`、`model_name`、`dimensions`、`retrieval_k`、`batch_size`
- 技能区里直接导入资料、搜索资料，并把结果用于项目上下文
- 项目资料库和作者参考库支持 `txt / md / json / csv / html / docx / pdf` 文件导入；PDF 在 `qwen-doc-turbo` 不可用或失败后会优先用 LiteParse 本地解析并写入页码标记，LiteParse 不可用时回到 `pypdf`，本地文本为空时才尝试 LiteParse OCR。
- 技能区 `长篇稳定档案` 会使用项目内 `Vault/` 作为默认 Obsidian Vault，新建作品时自动创建常用目录和同步配置；界面没有启用开关，普通作者不需要配置路径过滤、状态过滤或 AI 可用标记过滤，这些规则保留在高级同步规则里。同步后会解析 Markdown frontmatter、正文内联属性、Dataview 段落内属性、`summary / description / abstract / keywords / search_terms / 关键词` 等摘要 / 检索词 Properties、`summary:: / keywords::`、`[summary:: ...]`、`(keywords:: ...)`、`[[双链]]`、Markdown 内链、标签、可解析外链、反向链接、未解析链接、歧义链接、章节范围、剧透边界、`required_phrases / 必须出现` 和 `forbidden_phrases / 禁止出现`，写入项目本地 `knowledge.db`。frontmatter 字段名支持大小写、空格、连字符和下划线等常见属性写法，frontmatter 或正文内联属性里的 `source_notes / related_characters / related_notes / depends_on / foreshadows / payoffs / reveals / related_locations / related_props / related_organizations` 等关系字段会参与图谱解析，并把依赖、伏笔、兑现、揭示、相关地点等关系语义保留到笔记摘要、知识索引、章节上下文和界面预览；章节上下文只显示目标章节可见的关系目标，章节安全内容会隐藏指向未来笔记的正文或摘要 `[[双链]]` 和 Markdown 内链，但保留真正未解析或歧义双链的图谱风险。
- 架构总览有“稳定档案”页签，直接读取 `story_overview.obsidian`、`story_overview.obsidian_maintenance_summary` 和 `story_overview.obsidian_maintenance_suggestions`。该页签显示 Vault 同步状态、图谱解析统计、AI 维护摘要、待处理维护建议和正式笔记；以维护刷新模式读取项目详情时，模型总览里未入 Vault 的人物、事件、地点、道具、技能、场景和组织会在模型总览当前有效时自动发布为项目内 Vault 正式档案；模型总览过期时只展示旧结构，不写入草稿或 Vault。仍需人工确认的待审架构实体草稿会作为写作图谱节点展示，目标章节可见时也会以低优先级软提醒进入章节上下文。作者可在这里保存维护草稿、发布到 Vault、确认合并、忽略或恢复建议。默认项目内 `Vault/` 的 Markdown 笔记可在架构总览中打开编辑，保存后会重新同步长篇稳定档案和知识索引；外部 Vault 不通过项目文件编辑器写入。
- 路径过滤按大小写不敏感匹配。默认排除 `.obsidian/**`、`.trash/**` 和 `templates/**` 时，也会排除 `.OBSIDIAN/`、`.Trash/`、`Templates/` 等常见目录写法；用户自定义 `drafts/**` 这类规则时也会匹配 `Drafts/`，避免模板、插件状态或草稿目录混入知识索引。候选笔记超过 `max_notes` 时，会先按 Vault 相对路径稳定排序再应用数量上限，并在同步警告里提示有候选笔记未同步；候选总数和 `max_notes` 会进入来源签名，让界面的 skipped 和警告随 Vault 增删更新。
- AI 可用标记过滤支持正向和反向 Properties / 标签：`usable_by_ai / ai_usable / AI可用 / 可供AI使用 / 可供模型使用 / 写作可用` 或 `#AI可用` 为真时视为可用；`no_ai / not_for_ai / exclude_from_ai / AI不可用 / 不供AI使用 / 不允许AI使用 / 勿用AI`、`#no-ai` 或 `#AI不可用` 为真时排除笔记；`no_ai: false` 或 `AI不可用: 否` 会被视为明确可用。Markdown frontmatter、正文内联属性、正文标签和 Canvas 文本节点属性使用同一规则。
- 状态过滤支持显式状态别名、布尔状态 Properties、标签和目录推断。`status: 正式设定 / official / final` 会按正式可用状态处理，`status: wip / archived` 会按过滤状态处理；没有显式 `status / 状态` 字段时，`canonical: true / published: yes`、正文或 Canvas 文本节点 `canonical:: true` 会按正式可用状态处理，`draft: true / private: true / archived: true`、正文或 Canvas 文本节点 `draft:: true` 会按过滤状态处理；缺少显式状态和布尔状态时，`#canonical / #正式 / #已发布` 或 `正式设定/`、`Published/` 等标签 / 目录会按正式可用状态处理，`#draft / #草稿 / #private / #私密 / #废案` 或 `Drafts/`、`草稿/`、`Private/` 等标签 / 目录会按过滤状态处理；显式 `status` 字段优先，不会被布尔属性、标签或目录覆盖。
- frontmatter 数组支持 YAML flow sequence 的常见写法，`aliases: ["潮师, 守账人"]`、`keywords: ["旧船队, 暗账"]`、`required_phrases: ["潮声异常, 不得提前解释"]` 不会把引号里的逗号误拆成多项；普通列表型 Properties 可用逗号、顿号、半角分号或中文分号分隔多值，例如 `source_notes: 当前线索；未建笔记` 会生成两个关系目标。
- frontmatter 多行文本支持 YAML block scalar。作者用 `summary: >`、`description: |`、`summary: >2-`、`keywords: |2-` 写多行摘要或带缩进标记的多行字段时，这些内容会进入知识索引、笔记选择和章节安全预览；`keywords / source_notes / required_phrases` 等列表型字段使用多行文本时，会按行进入检索词、图谱关系和写作约束；这些列表字段的单项也可以写成 `- >` 或 `- |`，用于维护较长的检索词、来源笔记、必写项或禁写项。
- frontmatter 支持 YAML 对象列表和顶层嵌套对象。章节计划、章节合同、剧情债务和人物弧线笔记把 `scenes / required_beats / character_checks / debts_to_advance` 写成 `- goal: ...`、`conflict: ...`、`payoff: ...` 这类多字段对象，写成单独 `-` 后换行维护对象字段，或用 `required_beats: [{goal: ..., evidence_sources: [{source_note: ...}]}]`、`- {goal: ..., payoff: ...}` 这类 YAML flow mapping 时，系统会把对象字段转成章节上下文可读的结构化行；对象字段值可以用 `goal: >`、`reason: |` 这类 YAML block scalar 维护多行场景目标、理由或验收说明；对象里继续嵌套 `character_checks / evidence_sources` 等对象列表时也会递归解析，嵌套列表同样支持单独 `-` 后换行写对象字段；`chapter_contract:` 这类顶层对象里的 `chapter_range / objective / required_beats / acceptance_checks / evidence_sources` 等直接子字段也会进入章节范围、章节上下文和图谱关系；对象里的双链和 Markdown 内链会进入链接、反向链接和图谱关系统计，目标是未来笔记时仍按章节安全内容隐藏。
- 没有显式 `type / kind / 类型` 的 Obsidian 笔记会按常见目录或标签推断类型。`Characters/`、`Locations/`、`Plans/`、`Debts/`、`CharacterArcs/`、`Style/`、`XP/` 等会进入人物、地点、章节计划、剧情债务、人物弧线、文风规则和 XP 规则类型；`#人物/主角`、正文 `#人物／主角`、`#章节计划/58`、`#剧情债务/伏笔` 这类层级标签会按半角或全角斜杠分段参与推断；作者写了 type 时不会被目录或标签覆盖。Obsidian 多选 Properties 里的 `type: [主角, 人物]`、`type: [临时, 章节计划]` 会扫描整个列表并识别系统已知类型，完全未知的显式 type 会保留原值。
- 章节计划类层级标签会同时参与章节范围解析。作者只写 `#章节计划/58`、`#章节合同/58-60`、`#场景卡/59` 或 `#scene-plan/59` 时，系统会识别为章节计划 / 合同 / 场景卡，并按标签里的数字限制可见章节，不要求再写 `chapter_range`。
- 章节安全内容会处理 Obsidian 元数据里的 `tags / aliases / keywords / required_phrases / forbidden_phrases`。这些字段中如果写了指向未来笔记的 `[[双链]]`、Markdown 内链，或直接写到已知未来笔记的纯文本标题 / 路径名 / 文件名，目标章节上下文会改写成“未开放设定”，标签预览和本章 Obsidian 写作约束不会直接显示后段笔记标题。
- frontmatter 行尾 YAML 注释会被忽略。`status: canonical # 正式设定`、`chapter_range: 58-60 # 中段`、列表项后的 `# 说明` 不会污染状态过滤、章节范围、图谱关系或写作约束；引号里的 `#` 和 `[[笔记#标题]]` 会保留。
- Obsidian 标签属性和正文标签支持空格、分号、未加引号井号标签和常见正文标签写法。`tags: "#人物 #第58章 #剧透/57"`、`tags: #章节/44-45 #剧透/43`、多行 `tags: - #人物/配角`、`tags: 人物 主角`、`tags: "人物；第58章"`、`tags:: #支线 #第59章` 和正文 `#人物／主角 #适用章节／40～42 #剧透／39` 会拆成单个标签，前导 `#` 会去掉后参与标签展示、类型推断、章节范围和剧透边界识别；非标签字段里的 `#` 仍按行尾注释处理。
- 关系字段支持 Markdown 内链。`source_notes: "[当前线索](Clues/当前线索.md)"`、`related_characters:: [林追](../Characters/林追.md)`、`[林追](/Characters/林追.md)` 会保留关系语义，并按当前笔记路径、同目录相对路径或 Vault 根路径生成可解析链接和反向链接。
- 关系字段里的普通字符串和列表项按逗号拆分多值时，会保留 Markdown 内链标签、双链别名和目标路径内部的逗号。`source_notes: "[线索乙, 潮账](../Clues/线索乙.md)"`、`related_characters: ["[林追, 主角](../Characters/林追.md)"]`、`depends_on: "[[线索甲|账册, 初证]]"` 仍会生成图谱关系、可解析链接和反向链接。
- Obsidian / Dataview 正文内联属性里的关系字段也会保留嵌套链接。`[source_notes:: [当前线索, 潮标](当前线索.md)]`、`(related_characters:: [林追, 主角](林追.md))`、`depends_on:: [[线索甲|账册, 初证]]` 会进入图谱关系、可解析链接和反向链接。
- 可见 callout 里的任务列表会按正文解析。`> - [ ] source_notes:: [[当前线索]]`、`> - [!] related_characters:: [[林追]]`、`> - [?] required_phrases:: 潮声异常`，以及 `> ## 必须包含`、`> ## 禁止出现` 下的任务项，会进入内联属性、图谱关系、写作约束和章节安全内容；`[!] / [?] / [>] / [/] / [-]` 这类常见 Obsidian Tasks 状态也会识别，隐藏 callout 仍被排除。
- Markdown 表格会参与章节资料结构化。Markdown 笔记、Canvas 文本节点和可见 callout 中的章节合同、章节计划、剧情债务或人物弧线表格，如果包含 `章节目标 / 必须节拍 / 禁写动作 / 验收项 / 证据来源 / 相关人物` 等列，会转成现有上下文行、图谱关系和章节安全内容；单元格里的 `\|` 会还原为普通 `|`。
- Markdown 内链目标里的英文括号会作为文件名内容解析。`[林追旧档](../Characters/林追(旧).md)` 会指向 `Characters/林追(旧).md`，不会被第一个 `)` 截断；目标是未来笔记时仍按章节安全内容隐藏。
- Markdown 内链目标里的转义字符和 title 会按链接语义处理。`[林追旧档](../Characters/林追\(旧\).md "旧档")` 会还原为 `Characters/林追(旧).md`；`[终局答案](../Secrets/未来真相 "终局")` 会去掉 title 后解析，目标是未来笔记时仍按章节安全内容隐藏。
- Markdown 引用式链接会参与 Obsidian 图谱。正文写 `[林追旧档][old]` 或快捷引用 `[林追旧档]`，并在同一笔记定义 `[old]: ../Characters/林追\(旧\).md "旧档"` 或 `[林追旧档]: ../Characters/林追\(旧\).md "旧档"` 时，会生成可解析链接、反向链接和关系语义；引用定义指向未来笔记时，定义里的路径和 title 也会被章节安全内容隐藏。Markdown 脚注 `[^id]: ...`、缩进续行和正文脚注标记不会被当成知识图谱链接，也不会进入 AI 可见正文。
- HTML `<a href="...">` 链接会按 Markdown 内链处理。`<a href="../Characters/林追.md">林追</a>` 会生成可解析链接、反向链接和关系语义；指向未来笔记时会按章节安全内容隐藏标签和路径，指向本地附件时会被附件过滤。
- Obsidian URI 会按内部 Vault 链接处理。`obsidian://open?vault=Demo&file=Characters%2F林追.md` 和 `obsidian://advanced-uri?vault=Demo&filepath=Secrets%2F未来真相.md&heading=终局答案` 会解析到对应笔记；`heading / header / section / block / blockid / block_id` 或 URI fragment 会保留为小节 / 块引用。frontmatter 关系字段、Markdown 链接、HTML `<a>` 链接和 Canvas link 节点里的 URI 都会生成图谱链接、反向链接和关系语义，指向未来笔记时仍按章节安全内容隐藏。
- Obsidian 相对路径双链按当前笔记路径和路径段解析。`[[../Characters/林追]]`、`[[./当前线索]]`、`[[Clues/../Characters/林追]]`、`[[/Characters/林追]]` 会归一化为 Vault 内笔记路径，参与图谱链接、反向链接、关系语义和章节安全处理；相对双链指向未来笔记时，早期章节不会看到未来标题或别名。
- Obsidian URL 编码双链会先解码再解析。`[[Characters/林%20追]]`、`[[../Secrets/未来%20真相]]` 会按解码后的 Vault 路径进入图谱链接、反向链接、关系语义和章节安全处理；指向未来笔记时，早期章节不会看到未来标题、路径或别名。
- Obsidian URL 编码保留字符会先保留路径语义再解码。`[[Characters/林%23追]]`、`[线索](Secrets/未来%5E真相.md)` 这类文件名里的编码 `# / ? / ^` 不会被误当成 heading、query 或 block 分隔符；章节安全处理仍按解码后的真实目标执行。

### 目前边界

- 现在还是项目内混合检索，不是独立的外部向量库服务。
- Obsidian 默认作为资料源读取；项目内状态文件仍负责统一维护正式人物状态、剧情债务和章节合同，同时会吸收目标章节可见的 Vault 正式剧情债务和人物弧线笔记。叙事状态账本会把目标章节可见的 Obsidian 来源、必写项、禁写项、剧情债务、人物弧线、图谱风险和章节执行状态并入章节任务卡，自学习面板最新章节任务卡会展示这些 Vault 状态；缺失或触犯的 Obsidian 要求会转成后续章节可见的高优先级叙事债务，模型叙事编辑生成下一章合同时会读取当前章和下一章的 Obsidian 约束。长篇稳定档案可用时，账本会为未入 Vault 的剧情债务、人物弧线和图谱问题生成维护建议，包含建议笔记路径、处理动作，以及带来源 ID、来源章节、相关人物字段、人物双链或来源笔记路径的 Markdown 草稿；剧情债务和人物草稿会按来源章节写入 `reveal_after_chapter`，多个来源章节时按最晚来源章开放，剧情债务草稿同时写入 `debt_content / debt_status / risk_level / next_required_action`，人物状态草稿写入 `character / phase / current_state / unresolved_pressure / required_next_check` 并带 `人物状态` 标签，发布后按目标章节过滤，不会把后段自动维护笔记带入早期章节；维护摘要会写入 Agent 规划上下文；Agent 路由 / 规划给模型看的维护建议明细会按目标章节筛选，多章节指令会优先按生成、改稿、拆场或诊断的动作目标章节判断，没有明确目标章节的非架构任务只保留维护摘要，不暴露后段建议标题、路径或动作；Agent 路由 / 规划和自学习状态以维护刷新模式读取当前项目详情时，会刷新这些维护建议并可自动写入中高优先级待审草稿；重复出现的未解析双链会形成 `Graph/` 待审草稿并继承来源笔记的章节范围和剧透边界，来源章节范围不连续或多个开放式来源起点不同时会改用较晚可见的剧透边界，避免生成过宽章节范围；重名和歧义链接会形成修复提醒；已解析双链如果来源笔记可见范围没有被目标笔记可见范围覆盖，会形成章节范围不匹配风险；带未解析或歧义双链的笔记不会被计入孤立笔记；中高优先级建议会在章节保存、Obsidian 同步或章节上下文生成时自动写入项目 `.gaoxia/obsidian_drafts/` 待审草稿，用户仍可显式保存、忽略、恢复或更新草稿；自动草稿未被人工改动时会随图谱来源列表、来源内容和章节边界变化更新，人工改动过的草稿不会被自动覆盖；忽略同一路径建议后，后续来源变化产生的新建议会继承忽略状态并跳过自动草稿；恢复处理后，同路径新建议会重新进入待处理和自动草稿流程；保存草稿遇到同路径既有人工内容时也会保留原文并记录状态；项目内 `Vault/` 会在章节保存、Obsidian 同步、章节上下文生成或稳定档案维护刷新后自动发布系统生成且未被人工改动的中高优先级维护项；普通读取项目详情不再触发 Vault 写入；项目目录外 Vault、人工改动草稿、合并项、缺失项和低优先级规则仍需要用户显式发布或确认。发布会检查目标路径在 Vault 内且不覆盖已有笔记，并重新同步 Obsidian 摘要和知识库，让新笔记进入图谱解析，Graph 新笔记会按继承的章节边界控制可见范围；发布过的 Vault 笔记被移动或改名后会先按内容签名识别；新生成的维护笔记带 `gaoxia_maintenance_id`，发布到 Vault 前也会恢复缺失的身份字段，内容被作者改过但身份唯一匹配时也会改到新的 Vault 路径；如果对应维护项仍在列表中，自学习面板会显示移动前后路径；没有唯一匹配或文件被删除时会显示 Vault 笔记缺失并允许重新发布，自动发布内容被判定落后时会显示 Vault 待更新。

- 章节档案笔记可只维护 Properties。`chapter_note / chapter_summary / chapter_archive / author_archive` 笔记里的 `chapter_title / chapter_summary / chapter_events / state_changes / handoff_to_next / chapter_excerpt` 会转成知识索引、章节上下文、Agent 能力上下文和叙事状态账本里的“Obsidian 章节档案”提示；章节核验会检查明确指向当前章的强制类 `handoff_to_next`，正文没有承接可核验关键词时会作为 Obsidian 必需设定问题进入自动修订判定；系统自动章节档案草稿也会写入 `handoff_to_next`，其中“下一章关注本章后果”类交接只进入上下文，不触发自动修订，发布后后续章节能读取结构化回顾，不依赖作者再写正文段落。
- 目标章节可见的 Obsidian 剧情债务和人物弧线笔记会进入 Agent 路由 / 规划上下文、叙事状态账本提示、章节任务卡和章节保存后的账本状态；系统识别 `type: narrative_debt / plot_debt / character_arc / character_state`、`Debts/`、`PlotDebts/`、`CharacterArcs/`、`剧情债务/`、`人物弧线/` 路径和相关标签，并继续按章节范围和剧透边界过滤。剧情债务笔记只写 `debt_content / debt_status / risk_level / expected_payoff_range / next_required_action / related_characters`，或人物弧线笔记只写 `character / phase / current_state / unresolved_pressure / required_next_check` 时，这些 Properties 也会进入知识索引、账本状态、章节任务卡和模型叙事编辑输入；系统生成的债务与人物状态草稿也会写入这些 Properties，人物状态草稿带 `人物状态` 标签，显式发布后可作为同类 Vault 来源读取。规划上下文会给出目标章节可见的 Obsidian 来源、章节计划、必写项、禁写项、剧情债务、人物弧线和图谱风险；自学习面板的最新章节任务卡会展示这些条目，模型叙事编辑生成下一章合同时也会读取下一章可见的这些结构化条目。
- Agent 路由 / 规划上下文会识别多章节目标和章节范围，例如“第 58 到 60 章”；包含“蓝图 / 架构”等词但明确写了章节范围时，也会优先按目标章节读取 Obsidian 任务；能力上下文最多展开前 3 个目标章节的 Obsidian 任务摘要，包含来源、章节计划、章节档案、必写项、禁写项、剧情债务、人物弧线和图谱风险，维护建议按这些目标章节共同筛选和排序，避免批量章节任务只看到单章资料；明确要求生成正文的 2 到 3 章范围会展开成逐章生成动作，每章再分别进入去 AI 和一致性复查，超过 3 章会提示分批或先整理章节蓝图；执行阶段跨到下一章时，会按新目标章刷新资料库和 Obsidian 分析摘要，并缓存给同章生成、改稿和复查使用。
- Agent 章节生成、draft 写回或改稿写回后，如果当前保存生成或更新了 Obsidian 维护草稿，执行结果会返回 `obsidian_maintenance` 产物，列出相关待审草稿、状态和路径，作者不必离开当前执行结果就能看到系统整理出的 Vault 候选资料；产物卡片也可打开 Agent 自学习面板，并按当前章节筛选维护项。
- 两篇以上没有正文双链、frontmatter 关系、未解析或歧义双链和反向链接的正式 Obsidian 笔记会形成 `Graph/孤立笔记整理-{来源摘要}.md` 待审索引草稿。草稿会继承来源笔记章节范围或剧透边界，发布后通过 `source_notes` 和正文双链为原笔记建立 backlinks，让人物、地点、道具等孤立设定更容易被章节上下文的一跳图谱扩展命中；后续新增孤立笔记会使用新的来源摘要路径，不会被旧索引的已发布状态隐藏。
- 章节生成、改稿和诊断上下文会按目标章节显示 Obsidian 待审草稿提醒，用来提示资料维护状态；带章节范围或剧透边界的草稿（包括作者手工改动后的草稿文件）不会进入范围外章节提示，草稿 frontmatter 字段名支持大小写、空格、连字符和下划线等常见属性写法，提示会写明这些草稿不能当作 Vault 正式设定引用。目标章节可见的 `create_chapter_note` 草稿会附带章节档案短预览，让后续章节读取上一章摘要、交接和未完成必写项；作者删除 frontmatter 后，系统会从正文同名小节和“章节正文摘录”小节读取这些预览字段。目标章节可见的 `create_chapter_contract_note` 草稿会附带合同预览，读取章节目标、必须节拍、禁写动作和验收项；作者删除 frontmatter 后，系统会从合同正文小节读取。目标章节可见的 `create_style_rule_note` / `create_xp_rule_note` 草稿会附带文风 / XP 预览，读取规则、适用范围、检查项、证据数和置信度；作者删除 frontmatter 后，系统会从正文里的“文风规则 / XP规则 / 使用建议”等行读取。目标章节可见的 `create_story_*` 架构实体草稿会显示人物、地点、道具、组织、事件、技能或场景档案摘要。其它草稿只显示维护状态，不显示章节档案、章节合同、文风 / XP 或架构实体预览。
- 如果待审草稿文件缺失，章节提示不会只凭建议路径展示草稿；系统会继续读取维护项里的 `source_chapters` / 正文“来源章节”，并按最晚来源章节过滤。
- 如果作者手工删除待审草稿 frontmatter，章节提示也会继续扫描正文里的 `source_chapters::` 或“来源章节：...”，按最晚来源章节过滤；章节档案草稿还会继续从正文小节读取摘要、交接和未完成必写项预览。
- 写作上下文不会简单按文件顺序塞入所有 Obsidian 笔记；系统会用当前任务、章节标题、当前章尾段、上一章尾段和检索词匹配相关笔记，匹配范围包含标题、路径、别名、标签、双链、Markdown 内链、frontmatter 摘要、关键词、正文摘要、必需 / 禁止短语和中文词组重合度。明确绑定目标章节的笔记会提高选择优先级；只有 `reveal_after_chapter`、`#剧透/57` 或 `#第57章后可用` 的笔记，在目标章节开放后也会获得章节相关性权重，让章节档案和后段设定不会因为没有显式 `chapter_range` 被无关全局资料挤掉。命中笔记会带入目标章节可见的一跳外链和反向链接，减少无关设定污染当前章节。Agent 的 `review_knowledge` 在没有可用蒸馏摘要时，也会按任务说明和目标章节选择 Obsidian 笔记，而不是按文件顺序读取。
- Obsidian 笔记可用 `chapter_range / chapter_start / chapter_end / reveal_after_chapter`，这些字段可写成 `Chapter-Range`、`Reveal After Chapter` 等常见属性名，也可写成 `chapter_range:: 58-60`、`[chapter_range:: 58-60]`、`(reveal_after_chapter:: 57)` 这类正文内联属性；开放范围可写成 `chapter_range: 58+`、`chapter_range:: 第59章以后`。正文也支持“适用章节：第 58-60 章”“第 57 章后可用”，标签支持 `#章节/58-60`、`#第58章`、`#第58章起`、`#Ch58-60`、`#Ch58+`、`#剧透/57`、`#第57章后可用`。章节上下文、Agent 资料分析、普通知识检索、任务蒸馏、连续性证据包和章节核验都会按目标章节过滤未来设定；知识检索预览、连续性证据正文和任务蒸馏里来自 Obsidian 的摘要都会改用章节安全内容，正文中指向未来笔记的 `[[双链]]` 或 Markdown 内链会改写为“未开放设定”，未解析或歧义链接仍保留为维护线索；有目标章节时，知识检索和证据检索会先读取更大的候选池再按章节过滤，章节上下文内部的知识检索也会传入目标章节，Obsidian 检索命中如果无法对应到当前总览里的可见笔记，会被丢弃，避免早期章节从旧索引提前拿到后段真相，也避免大量后段笔记把当前章节资料挤出结果。技能库和架构总览的检索入口会把当前选中章节传给 `/api/projects/{project_id}/knowledge/search`，返回结果按同一章节安全内容替换预览；联网考据接口也支持 `chapter_index`，会用章节安全本地命中生成考据提示；`review_knowledge` 紧跟章节生成、改稿或一致性检查时继承后续章节范围，紧跟整书架构时保留全书资料视角。
- 章节档案的 `source_ids` 可写成 `chapter-058`、`chap-058`、`ch058`、`Chapter 58` 或 `第58章`，同步时会推断来源章节；多个章节来源 ID 按最晚来源章开放，普通业务 ID 只有包含 `ch` 片段时不会被当作章节。
- 章节档案的来源章节字段可写成 `source_chapters`、`章节来源`、`来源章` 或 `来源章节号`；正文里的 `来源章：第 58 章、第 60 章` 也会按最晚来源章开放。
- 正文标签、章节标签和文件名 / 路径里的区间分隔符支持半角连字符、波浪线、中文全角波浪线、长横线和“至 / 到”，例如 `#第58～60章`、`#Ch58～60`、`#适用章节／40～42`、`第58～60章-计划.md` 和 `ch58～60-plan.md` 会按对应章节范围过滤。
- 命中的 Obsidian 笔记会进入“本章 Obsidian 设定检查清单”，列出来源笔记、必须出现、禁止出现、关联笔记、关系语义、反向关联和图谱注意项；歧义双链和未解析双链会在生成前暴露给写作模型。发布到 Vault 的维护笔记即使只在 frontmatter、正文内联属性或正文关系小节里保留来源笔记和相关人物，也会参与关联笔记和反向关联。
- 相关 Obsidian 笔记里的必需 / 禁止短语会进入单独的“本章 Obsidian 写作约束”块。它和资料摘要分开出现，避免模型把禁止项当普通背景资料处理。
- 章节核验里的 Obsidian 必写 / 禁写问题会计入必须修订问题，即使总体分数没有低于自动修订阈值，也能让章节自动修订读取核验报告并重新写回正文。
- 如果多个笔记共享同一标题、文件名或别名，指向该名称的双链会标为歧义，不会自动解析到任意一篇；技能面板会显示重复命名和歧义链接数量，方便作者整理 Vault。
- 同步摘要带 `source_signature`。读取架构总览、技能面板或写作上下文时，如果 Vault 内符合过滤条件的 Markdown 文件变化，会自动刷新 `.gaoxia/obsidian_sync.json`。
- 同步摘要会生成 `issues` 结构化问题列表，列出重复命名、歧义链接、未解析链接和孤立笔记，技能面板和架构总览都能展示涉及的笔记路径。
- 搜索索引仍保存在项目本地 SQLite，不依赖独立外部向量库。

## 2. 分步架构引擎

### 目标

整本架构不再只是一键生成四段文本，现在可以按模块逐步生成、逐步修改、逐步写回。

### 当前步骤

技能区 `分步架构` 支持这些模块：

- `core_seed`
- `character_design`
- `world_building`
- `plot_structure`
- `character_state`
- `blueprint`
- `global_summary`

### 工作方式

- 前端先把当前项目文档同步到一个 `workspace`
- 用户选择要生成的步骤
- 后端只生成这个步骤对应的内容
- 返回：
  - `headline`
  - `summary`
  - `content`
  - `checklist`
- 如果模型把架构段落返回成嵌套 JSON、数组或对象，后端会先转成可写入设定文件的文本，避免把外层响应结构直接存入项目文档。
- 前端可以只替换当前模块，也可以一次性把整个工作区写回项目
- Agent 执行整书架构时会按 `core_seed -> character_design -> world_building -> plot_structure -> character_state -> blueprint -> global_summary` 逐步生成；任务开始时只构建一次项目上下文快照，后续步骤复用快照，并通过 workspace 使用本次任务里前面步骤刚生成的内容。每个步骤会按当前模块裁剪无关 workspace 和超长上下文，并使用对应的输出 token 上限，避免世界设定、人物设定等短模块占用章节蓝图级别的模型预算。
- 每完成一步就直接写入对应设定文件，并把进度写到 `.gaoxia/architecture_progress.json`。整书架构执行期间会保持前台模型会话，后台辅助巡检不会插入步骤间隙；知识库索引、模型版故事总览和系统记忆刷新会在整轮完成后统一排队。如果整书架构执行中途失败，下一次同一指令会重新读取项目文件和进度，跳过已经写入且仍有内容的步骤，从失败步骤继续执行。
- 情节骨架、人物状态和章节蓝图步骤必须沿用人物设定里已经确定的核心人物名单；如需新增配角，只能作为单次情节功能角色，不能默默替换核心人物或改名。
- 架构步骤构建上下文时只读取现有知识库的关键词结果，不同步重建索引，也不触发 query embedding。
- 架构总览读取项目设定时，只使用缓存里的结构化总览；人物状态、关系、事件、地点、道具、技能和组织都必须带来源证据，证据校验通过后才进入总览。没有可用模型总览时，人物和世界要素列表保持为空，不再用本地文本规则生成。Obsidian 同步状态和笔记摘要会随 `story_overview.obsidian` 返回，并在知识检索页展示；架构总览里的长篇稳定档案卡片会展示章节范围、来源章节、必写 / 禁写短语、考据来源和图谱风险；“稳定档案”页签会展示并处理 AI 维护建议，也能编辑项目内 `Vault/` Markdown；架构总览页发起知识检索时会带上当前选中章节，让 Obsidian 预览按章节边界过滤。
- 模型总览会按项目来源签名缓存在 `.gaoxia/story_overview_model.json`，设定、资料、Obsidian 笔记或章节变化后签名失效；新总览由辅助任务后台生成，不阻塞架构和写作主任务。生成时优先使用第二审查模型；第二审查模型不可用时，使用当前写作模型。项目来源会按约 4500 字符分片请求模型，再合并通过证据校验的节点。
- 章节生成、改稿、诊断上下文和项目级文风 / XP 提示会显式关闭模型总览缓存，只读取本地文档、章节、项目记忆和目标章节可见的 Obsidian 摘要。项目记忆的自动条目也不从模型总览实体生成；续写、改稿、仿写和人物任务的项目蒸馏包不会从模型总览实体生成，没有目标章节时也不会默认带入 Obsidian 后段笔记。整书架构蒸馏保留全书资料视角，避免后段地点、道具、组织或关系进入早期章节写作链路。

### 继续扩写

- `mode=continue` 时，分步架构会带上新增章节目标
- 写回项目时可以直接同步更新 `target_chapters`

### 使用位置

- 技能区 `分步架构`
- 后端接口：
  - `POST /api/generate/architecture/step/stream`
  - `PUT /api/projects/{project_id}/architecture/workspace`

## 3. 文风 DNA 校准

### 现在有的能力

- 样文分析
- DNA 分析
- 文风融合
- 文风校准
- 叙事校准
- 校准回滚
- 作者参考库
- 作者参考库语义检索
- 系统学习版文风 / XP
- 剧情债务与人物弧线

### 数据结构

每个文风方案现在会保存这些核心字段：

- `instruction`
- `analysis`
- `dna_analysis`
- `narrative_for_architecture`
- `narrative_for_blueprint`
- `narrative_for_chapter`
- `source_sample`
- `calibration_reference`
- `calibration_notes`
- `last_calibrated_at`
- `pre_calibration_snapshot`

### 三段式叙事约束

文风方案现在不只管“语言像不像”，还会分别约束：

- 架构阶段怎么写
- 蓝图阶段怎么写
- 正文阶段怎么写

这三段内容会直接被生成链路读取。

### 作者参考库检索

- 作者参考资料现在不只是列表展示。
- 技能区里可以直接按关键词或语义搜作者参考。
- 后端会给作者参考资料补向量，查询时做混合排序。
- 文风方案在参与章节、蓝图、架构生成时，会优先带上命中的作者参考片段。

### 系统学习版文风 / XP

- 章节保存后，后端会从最终正文统计句长、短句比例、段落长度、对白密度和章尾压力信号，并结合章节核验、文风名和 XP 预设维护 `.gaoxia/learning/style_xp_evolution.json`。技能库写回生成章或改稿章时会把当前 XP 预设作为 `xp_preset` 传给后端，保存响应也会带回最新 `self_evolution` 元数据，供自学习面板立即显示新的章节任务卡和 Obsidian 维护摘要。
- 规则在两个不同章节重复出现后变为 `active`，后续 `build_prompt_support()` 会把这些规则加入章节生成、润色、定稿、去 AI 和蓝图任务。
- 目标章节明确时，`build_prompt_support()` 和 Agent 路由 / 规划上下文都会读取该章节可见的 Obsidian 文风 / XP 笔记；`type: style_rule / xp_rule`、`Style/`、`XP/`、`文风/`、`写作规则/` 路径和相关标签都会被识别。作者只在 Properties 里维护 `style_rule / voice_rule / tone_rule / sentence_rhythm / imagery / dialogue_rule / avoid_style / examples / applies_to`，或 `xp_rule / precheck / postcheck / workflow / technique / avoid_xp` 时，系统会读取同步后的结构化正文，把这些字段转成文风 / XP 参考内容，不只依赖摘要或短预览。可见规则超过提示容量时，目标章节范围更贴近的规则会排在通用规则前面，容量允许时文风和 XP 各保留最相关条目。没有目标章节时也会读取同步记录中无章节边界的全局规则，并排除带章节范围或剧透边界的后段规则。
- 这类规则排在作者明确要求、手工文风和手工 XP 之后；它只影响后续生成提示，不改作者记忆、文风方案、XP 预设或章节正文。
- Obsidian 文风 / XP 笔记同样只影响提示，不写入 `.gaoxia/learning/style_xp_evolution.json`，并按章节范围和剧透边界过滤。
- 系统学习版文风 / XP 规则变为 `active` 后，如果没有匹配到 Vault 规则笔记，会生成 `Style/` 或 `XP/` 低优先级 Obsidian 待审草稿；草稿带来源规则、来源章节、按最晚来源章生成的剧透边界、`source_ids`、`style_rule` 或 `xp_rule` Properties，发布前会在章节生成上下文和 Agent 规划上下文显示非正式文风 / XP 预览，作者发布后才作为 Vault 正式规则进入后续提示。发布后的规则笔记如果保留 `source_ids`，作者改名、移动或重写规则表达后，维护队列仍会识别为同一条系统学习规则。
- 规则整理不增加模型调用，章节核验失败时仍会记录正文特征和错误信息。

### 剧情债务与人物弧线

- 章节保存后，后端会维护 `.gaoxia/learning/narrative_state.json`。
- 剧情债务会把伏笔、承诺、关系变化和世界规则记录成结构化条目，包含状态、风险、预计处理区间、证据和下一步处理要求。
- 人物弧线会记录主要人物当前阶段、上次出现章节、未处理压力和后续检查项。
- 章节任务卡会按章节位置给出本章阶段、本章任务、避免事项和下一章交接；如果目标章节已有正文，也会记录 Obsidian 必写项已满足 / 未完成和禁写项已触犯的情况。未完成或触犯项会进入剧情债务列表，修订满足后自动标为已兑现。长篇稳定档案可用时，未匹配到可用 Vault 笔记的中高风险剧情债务、人物弧线和 Obsidian 图谱问题会形成维护建议；账本会同时生成维护摘要，统计待处理、高优先级、自动草稿、草稿缺失、Vault 笔记缺失、Vault 笔记已移动、Vault 待更新和已忽略数量，并给出优先处理项；Agent 路由 / 规划有目标章节时，会按目标章节可见维护项重新统计摘要并筛选建议明细，多章节指令会优先按生成、改稿、拆场或诊断的动作目标章节判断，没有明确目标章节的非架构任务只保留全局维护摘要，不暴露后段建议标题、路径或动作；维护队列按 80 章长篇规模保留章节档案建议和操作记录，一次自动保存更多中高优先级草稿；中高优先级建议会自动保存为项目 `.gaoxia/obsidian_drafts/` 下的 Markdown 草稿，也可由用户在自学习面板按筛选结果批量保存，把当前筛选结果里已保存的草稿显式批量发布到 Vault，批量确认当前筛选结果里的 Vault 合并项，批量忽略暂不处理的维护建议，或批量恢复当前筛选结果里的已忽略建议；项目内 `Vault/` 可在章节保存、Obsidian 同步、章节上下文生成或稳定档案维护刷新后自动发布符合条件的系统草稿；普通读取项目详情不再触发 Vault 写入；项目目录外 Vault、人工改动草稿、合并项、缺失项和低优先级规则仍需显式发布或确认，且发布不会覆盖已有笔记。剧情债务草稿会写入 `source_ids`、`source_chapters`、`related_characters`、相关人物双链、按来源章节生成的 `reveal_after_chapter`，以及 `debt_content / debt_status / risk_level / next_required_action` Properties；人物状态草稿会写入来源 ID、来源章节、同样的剧透边界、`character / phase / current_state / unresolved_pressure / required_next_check` Properties，并带 `人物状态` 标签；重复出现的未解析双链草稿会写入 `aliases`、`source_notes`，并继承来源笔记的章节范围和剧透边界；如果来源章节范围不连续，或多个开放式来源起点不同，草稿会改写为较晚可见的剧透边界，不生成横跨早段到后段的连续范围；已解析双链如果来源笔记可见范围没有被目标笔记可见范围覆盖，会形成章节范围不匹配风险；带未解析或歧义双链的笔记不会被计入孤立笔记；自动草稿未被人工改动时会随新增来源、来源内容和章节边界变化更新 `source_notes`，人工改动过的草稿不会被自动覆盖，保存草稿遇到既有人工内容时会保留原文；同一路径建议即使 ID 变化也会沿用已有草稿状态；被忽略的同路径建议不会自动写草稿，也不会进入 Agent 优先处理项，恢复处理后会重新进入待处理和自动草稿流程；草稿文件被移动或删除时会显示草稿缺失并允许重新保存；发布过的 Vault 笔记被移动或改名后会先按内容签名识别，新生成的维护笔记带 `gaoxia_maintenance_id`，发布到 Vault 前也会恢复缺失的身份字段，内容被作者改过但身份唯一匹配时也会把维护记录改到新的 Vault 路径；剧情债务和人物状态笔记如果保留 `source_ids`，作者改名、移动或改写标题后仍会被识别为同一条账本来源；如果对应维护项仍在列表中，面板会显示移动前后路径；没有唯一匹配或文件被删除时会显示 Vault 笔记缺失并允许重新发布；自学习面板会显示完整维护列表和维护摘要，支持按状态筛选并按标题、路径、章节或动作搜索，也会显示自动草稿、人工改动草稿、保留人工草稿、草稿缺失、Vault 笔记缺失、Vault 笔记已移动、Vault 待更新、已忽略、确认 Vault 已合并、恢复处理和批量恢复入口；发布后可被同步器解析为图谱关系，并继续按章节边界参与后续检索。
- Agent 自学习面板没有筛选时显示全局 Obsidian 维护摘要；存在状态、来源章节或搜索筛选时，摘要按可见维护项重新统计。从 `obsidian_maintenance` 产物卡片打开指定章节维护队列后，摘要总数与列表显示数一致。
- 对于已经保存但尚未进入 Obsidian 的章节，账本会额外生成章节档案草稿，保存到 `.gaoxia/obsidian_drafts/ChapterNotes/`。这类草稿不是正式设定，只有发布到 Vault 后才会进入图谱和知识索引；它的 `chapter_index / chapter_title / chapter_summary / handoff_to_next / chapter_excerpt` 会记录章节回顾和下一章交接，`obsidian_required_satisfied / obsidian_required_missing / obsidian_forbidden_violations` 会记录本章 Obsidian 要求执行状态，`source_ids` 会记录来源章节 ID，`source_chapters` 会保留可读来源章节，`source_chapter_hash` 会记录对应的章节正文版本，`source_notes` 会连接本章实际使用过的 Vault 来源笔记，但不会引用其它章节档案，`related_locations / related_props / related_organizations` 会把正文里命中的地点、道具和组织转成图谱关系，`reveal_after_chapter` 会让第 N 章档案从第 N 章开始对后续章节可用，而不会提前暴露；开放后的章节档案会在无明确查询命中时优先于普通全局资料参与上下文选择。草稿未发布时，章节生成上下文和 Agent 规划上下文只读取 `create_chapter_note` 草稿的短预览，包含摘要、交接和未完成必写项，并保留非正式资料提示；其它待审草稿不参与这类预览。发布后的章节档案如果保留 `source_ids: [chapter-058]`、`source_chapters: [58]` 或正文“来源章节”，作者改名、移动或重写标题后，同步器仍会识别来源章节，维护队列也会把它当成同一章档案；作者把类型改成 `author_archive` 并删除 `source_ids` 时，只保留 `source_chapters` 也能被识别；如果同一笔记保留多个章节来源 ID 或来源章节，会按最晚来源章节控制可见范围，文件名和来源章节冲突时也按更晚的开放章节处理。
- 剧情债务草稿里的预计处理区间写入 `expected_payoff_range`，不会写入 `chapter_range`；`chapter_range` 只表示 Obsidian 笔记可见范围。这样第 20 章产生、预计第 40 章后兑现的债务，发布到 Vault 后第 21 章仍能看到并保护这条线。
- 如果设置页保存了主模型 Key，或启用了第二审查模型，章节保存后还会执行模型版叙事审查。模型会基于当前章节、项目文档和旧账本输出带证据的债务更新、人物弧线变化、合同执行回看和下一章章节合同；没有证据的条目会被丢弃。
- 长篇稳定档案可用时，模型生成的下一章章节合同如果没有匹配到目标章节可用的 Vault 章节计划或章节合同，账本会生成 `.gaoxia/obsidian_drafts/Plans/` 下的待审草稿。草稿使用 `type: chapter_contract`、目标章节 `chapter_range`、来源章节、`source_ids` 和 `gaoxia_maintenance_id`，未发布前会在目标章节待审草稿提醒里显示非正式合同预览，作者发布后才作为 Vault 正式章节计划进入目标章节提示；发布后系统不再为同一合同显示维护建议。发布后的合同笔记保留 `gaoxia_maintenance_id` 或 `source_ids` 时，作者改写正文后仍按同一合同识别。后端读取 `chapter_contract` 时会按小节或同名 Properties 整理“章节目标、必须完成的节拍、必须推进的债务、不能提前揭开的债务、人物检查、文风检查、禁止动作、验收项、证据来源、风险提示”，避免长合同后半段从章节提示里消失。
- `build_project_context_bundle()` 会读取目标章节对应的叙事状态账本，把章节合同、必须处理、可轻触、不要提前揭开的剧情债务加入上下文。
- `build_project_context_bundle()` 也会按目标章节把 Obsidian 待审草稿作为资料维护提醒加入叙事状态块，并按来源章节与目标章节的相关性排序，显示来源章节；带章节范围或剧透边界的草稿（包括作者手工改动后的草稿文件）不会进入范围外章节提示，草稿 frontmatter 字段名支持常见属性写法，并明确标注不能按正式 Vault 设定使用。每条提醒都会读取对应草稿文件并校验维护 ID / 类型；`create_chapter_note` 草稿会附带从真实草稿 frontmatter 或正文小节提取的章节摘要、下一章交接和未完成必写项短预览，`create_chapter_contract_note` 草稿会附带合同目标、必须节拍、禁写动作和验收项短预览，`create_style_rule_note` / `create_xp_rule_note` 草稿会附带规则、适用范围、检查项、证据数和置信度短预览，`create_story_*` 架构实体草稿会附带人物、地点、道具、组织、事件、技能或场景档案摘要。
- 章节续写和核验会共用“章节连续性合同”。合同会写明目标章节在全书中的位置、人物当前状态、全书已发生事实、蓝图锚点、近期章节承接、叙事状态账本、项目记忆和资料证据。续写提示词会把合同视为优先约束；章节核验新增 `章节连续性合同` 维度，只把章节合同、剧情债务、人物弧线和 Obsidian 必写词这类明确义务判为合同项；合同项缺失会进入自动修订触发条件，修订提示也会读取同一份合同，默认最多修订 2 轮，已启用但仍保存为旧 1 轮的配置会在读取时升级为 2 轮。
- 章节核验会反查作者项目记忆里的“硬规则 / 警告”禁写表达。项目记忆写了“不要提前揭示沈砚就是主谋”“沈砚不能被提前揭示为主谋”“林追不能被提前揭示为卧底”“铜钥匙不能被交给白石商会”“不要把林澈改名为林追”“顾临不能死亡 / 叛变”或“林追不会主动暴露身份”这类规则时，正文直接命中会在 `项目记忆规则` 维度记为 critical，并参与章节自动修订判断；改名类规则需要正文出现“林澈被叫成林追”“把林澈写成林追”这类明确替换语境才触发，林追正常出场不会单独触发；没有可自动反查的禁写表达时该维度不计入评分。
- `build_project_context_bundle()` 遇到缺失草稿时同样按维护项 `source_chapters` 判断可见章节，避免缺失状态绕过章节边界。
- `build_project_context_bundle()` 遇到无 frontmatter 草稿时，会退回正文来源章节判断，而不是把草稿当全局可见资料。
- 章节化证据检索会在 Obsidian 命中替换成目标章节安全内容后重新检查查询词；如果命中只来自被隐藏的未来标题或链接，这条证据不会进入连续性证据包。
- 这套状态不直接改正文，也不会自动写作者记忆；项目内 `Vault/` 会在章节保存、Obsidian 同步、章节上下文生成或稳定档案维护刷新后自动发布符合条件的系统维护笔记；普通读取项目详情不再触发 Vault 写入，项目目录外 Vault 和人工改动内容仍需用户显式发布或确认。模型不可用时继续使用规则账本、章节任务卡和 Obsidian 维护建议。

## 4. 上下文预算与模型错误分类

### 上下文预算

- `build_project_context_bundle()` 会按任务类型和写作模型配置容量计算上下文预算，返回 `budget_report`。
- 默认字符预算仍以任务类型为基准：架构、续写 `18000`，人物视角 `16000`，文风模仿 `20000`，改写模式 `22000`。
- 写作模型配置容量较大时，预算会在保守上限内提高；常规章节生成约可提高到 `40000` 字级别，架构任务上限 `36000`，不会按模型宣传窗口塞满。
- 当前章节正文过长时，会保留开头和结尾，中间用说明性占位文本替代。
- 检索线索过长时，会优先缩短检索块，避免资料片段挤掉任务指令和章节上下文。
- 若所有上下文块叠加后仍超过预算，会按信息块分配剩余容量，优先保留项目记忆、章节任务卡、章节合同、叙事状态、剧情债务、人物弧线、Obsidian 必写 / 禁写约束和当前章节状态，再处理正文片段、Vault 摘要和检索证据；只有极端情况下才整体缩短最终上下文。

### 模型错误分类

- 生成链路和做梦链路现在会把模型调用异常分类后写入 `prompt_history.jsonl`。
- 已分类字段包括 `error_kind`、`error_title`、`error_user_action`、`error_retryable`。
- 当前覆盖认证、账单、限流、上下文过长、模型不存在、网络连接中断、服务端错误、超时、请求格式错误和未知错误。
- 聊天模型、云端 Embedding、重排序、项目愿景、联网考据和 qwen-doc 文档抽取请求都会经过统一 JSON 传输层，对 SSL EOF、DNS 解析失败、远端提前断开、连接重置、429 和 5xx 短时错误默认最多尝试 5 次；等待间隔可用 `NOVEL_MODEL_RETRY_DELAYS` 调整，连续失败后再返回分类后的用户提示。本地 Embedding 不经过网络传输层，模型文件缺失或依赖缺失会直接返回本地加载错误。
- `Prompt 历史` 查询会同时匹配错误类型和错误标题，便于从日志里定位模型配置或服务状态问题。

### 模型运行调度

- `model_runtime_service` 统一管理聊天模型和检索模型的运行通道，默认主模型并发为 1，Embedding / rerank 检索并发为 1。
- `_invoke_model()`、辅助模型、项目愿景、Embedding、rerank 和 qwen-doc 文档抽取都会进入运行通道，`prompt_history.jsonl` 会记录 `runtime_task_id / runtime_lane / runtime_priority / queue_wait_seconds`。
- 前台写作、架构、Agent、改稿、章节核验等主模型任务进入同一聊天通道；检索任务在前台模型忙时等待。
- 辅助任务巡检和自学习后台排程会在前台模型或检索忙时延后；包含 `model_review` 的自学习排程只在空闲窗口执行。去 AI 智能巡检同样使用后台窗口，章节保存和做梦完成只排队 `humanize_review`，实际裁判由空闲巡检处理。
- 设置页可以调整主模型并发、检索并发、后台空闲等待、队列策略、队列容量、后台失败暂停时间和章节候选模式。后台模型失败暂停只影响后台任务继续发起请求，不阻止前台手动生成、改稿或刷新模型总览。

## 5. 章节续写候选与批量任务

### 章节生成候选

技能区 `章节生成` 现在使用可配置候选续写流程：

- 先按 `target_words / target_chapters` 计算单章容量，把容量提示写入项目上下文
- `chapter_generate` 未指定目标字数时，会按当前章节距离单章均值的缺口作为完整章目标；Agent 里普通“写第一章 / 生成第 N 章”请求，在整书架构已齐全且没有明确短稿或具体字数时，也按这个规则处理
- `chapter_generate` 和 `chapter_workflow` 的 draft 模式收到显式目标字数时，会按调用方的 `target_words` 生成短稿或片段，不会被项目单章均值覆盖；只有 `target_words=0` 才进入完整章预算
- `chapter_generate` 和 `chapter_workflow/draft` 支持生成前提示词预览。预览接口只组装上下文、连续性证据、长度要求和写作消息，不调用写作模型；作者确认后的编辑文本通过 `prompt_override` 作为正文写作模型的用户消息。批量生成可用 `prompt_overrides` 为每章提交不同文本。
- 用户明确写了短稿、片段、开头或具体字数时，后端尊重用户输入；“当前正文约 3870 字”“保存校验：当前正文约 3870 字”这类状态描述不会被当作用户字数要求
- 当目标超过单次安全长度时，后端会按不超过 5500 字规划小节；每节继承前文、独立生成和审校，再合并成完整正文。如果模型单节写短，后端会按实际正文长度继续追加小节，直到接近完整章目标或达到安全次数上限
- 先生成承接简报和场景计划
- 默认 `standard` 模式只生成 1 个候选正文，再按承接事实、人物口气、可读性三个维度依次审校
- `fast` 模式只保留 1 个候选和承接事实审校，适合降低模型请求数量
- `deep` 模式保留 3 个候选，分别偏向对白承压、动作压迫和段尾推进；候选和审校仍进入统一运行通道，不再直接并发打模型
- 章节核验优先使用第二审查模型配置或 `NOVEL_REVIEW_MODEL_API_KEY / NOVEL_REVIEW_MODEL_BASE_URL / NOVEL_REVIEW_MODEL_NAME`；未配置时才使用当前写作模型
- 章节核验包含本地 `Obsidian 设定` 维度。系统会先按目标章节过滤 Obsidian 笔记，再检查当前可用笔记里的 `forbidden_phrases / 禁止出现` 和 `required_phrases / 必须出现`；禁用短语只要出现在正文里，即使正文没有提到笔记标题，也会给出 `critical` 问题。正文提到笔记、连续性证据命中笔记，或少量连续章节范围明确绑定的笔记缺少必需短语时，会给出 `warning`。章节核验签名按目标章节可见的 Obsidian 笔记计算，后段专用笔记变化不会让早期章节核验报告过期
- 章节核验包含本地 `项目记忆规则` 维度。作者项目记忆的“硬规则 / 警告”中出现“不要 / 不能 / 不会 / 禁止 / 避免”等禁写表达时，系统会做短语反查，避免长篇中把人物改名、提前点破主谋 / 真凶 / 卧底 / 潮师等身份、把关键物品或线索交给禁用对象、让关键人物死亡 / 叛变 / 黑化 / 离队或触犯作者写明的身份暴露禁区；“某人不能被提前揭示为主谋 / 真凶 / 卧底 / 潮师”和“铜钥匙不能被交给白石商会”这类主语在否定词前、约束在后面的写法也会识别；改名类规则会识别“A 被改成 / 写成 / 叫成 B”，但不会因为 B 正常出现在同章就误报；正文里的“没有 / 并未 / 尚未暴露身份”“并不是主谋”“并不是卧底”或“没有把铜钥匙交给白石商会”这类否定状态表述不会当作违规；项目记忆变化会进入章节核验签名，已有报告会标记过期，刷新后重新按新记忆规则检查
- 审校结果按固定权重合成总分
- 主流程按通过状态、分数、严重问题数量和候选顺序择优
- 候选未通过且有返工重点时，会修订一次并重新执行三类审校

这条流程用于 `chapter_generate`。`chapter_workflow` 的 draft 模式默认仍保留单候选承接保护链路；如果用户明确要求完整章或 15000 字这类超长目标，也会进入小节生成流程。使用编辑后的 `prompt_override` 时，正文生成仍会读取章节计划和连续性证据，生成后继续执行承接冲突检查、三类审校和必要修订。

章节改写使用另一条写回校验：`rewrite_chapter` 保存正文后会读取实际正文长度，并和用户字数要求、项目单章均值比较。重写、改写、定稿整章时，保存后的正文低于完整章容量会触发自动续写；如果剩余缺口超过 5500 字，会把完整缺口交给小节生成流程，由流程按实际正文长度继续追加小节。补足过程中任一请求失败，或最终仍未达到容量阈值，都会恢复当前改稿开始前的正文，避免把不合格短稿或半截扩写留在章节里。去 AI、短稿、片段、开头等明确短文本请求不会触发扩写。模型自报的“约 15000 字”“完整章节”等修改说明不会原样进入最终反馈。产物 `metadata` 会记录 `saved_word_count`、`length_target_words`、`length_status` 和 `length_completion_*`，供后续回看和自我进化报告使用。

### 批量生成任务队列

`/api/studio/batch-generate/stream` 现在按任务队列处理章节：

- 请求可以带 `task_id`，不带时后端创建一个新的任务 ID
- 任务状态保存在应用数据目录 `batch_tasks/{task_id}.json`
- 每章有独立状态：`pending / running / completed / failed`
- 任务记录保存章节编号、章节 ID、尝试次数、最后错误、单章结果和人工评论
- 再次传入同一个 `task_id` 时，已完成章节会直接返回旧结果，不重新生成
- `retry_failed=true` 时才会重试失败章节
- 章节仍然按顺序生成，不并行写相邻章节，避免破坏上下文连续性
- 后续章节生成前会读取上一章已保存正文的尾段，用它参与 Obsidian 笔记选择和连续性证据检索；批量写到第 N+1 章时，第 N 章刚写出的地点、组织、道具或线索能进入下一章上下文。

前端批量生成面板会显示并回填任务 ID，也能提交人工评论和失败章节重试开关。

## 6. 故事总览抽取

- `StoryOverview` 不再用本地规则从人物设定、人物状态、架构文件、资料和章节里猜人物或世界要素。
- 普通项目详情读取只检查 `.gaoxia/story_overview_model.json`。缓存存在且来源签名匹配时，直接返回模型整理后的人物、关系、事件、地点、组织/势力、道具、技能和场景。
- 没有可用模型总览缓存时，项目详情仍返回文档、资料、项目记忆、章节审查和蒸馏信息；人物、事件、地点、组织、道具、技能和场景列表为空，前端显示模型总览未生成。
- 模型总览只把稳定人物放进 `characters`：人物状态有专属段落，或在两个以上来源文件中持续出现；只在单一旧设定里出现的旧名、职务泛称、临时配角和章节功能角色不进入人物关系图。
- 模型版故事总览、知识库索引刷新、系统记忆刷新和去 AI 智能巡检属于辅助任务，任务状态记录在 `.gaoxia/auxiliary_tasks.json`。FastAPI lifespan 会启动后台巡检，默认每 180 秒检查一次，失败后按退避时间重试；`NOVEL_AUXILIARY_WORKER_ENABLED=false` 可以关闭巡检。去 AI 智能巡检会读取 `.gaoxia/learning/humanize_review_patrol.json`，同一批样本默认 12 小时内不重复调用裁判模型。
- 模型版故事总览优先使用第二审查模型配置和 `NOVEL_REVIEW_MODEL_API_KEY / NOVEL_REVIEW_MODEL_BASE_URL / NOVEL_REVIEW_MODEL_NAME` 这组环境变量；第二审查模型不可用时，使用当前写作模型配置和写作模型 API Key。模型版故事总览请求超时时间为 240 秒，每个分片限制核心节点数量，避免把章节标题逐条展开。生成失败会写入 `.gaoxia/story_overview_model_failure.json`；后台辅助任务会按 `.gaoxia/auxiliary_tasks.json` 的任务时间后续再处理，手动打开架构总览或刷新模型总览会立即再次请求模型，不返回 `retry_after` 失败倒计时。没有生成 `.gaoxia/story_overview_model.json` 时，辅助任务不会记为完成。
- 模型输出仍要经过来源证据校验：没有在项目来源中找到证据的人物、事件和世界要素不会进入缓存。
- 架构总览里的结构化节点不直接写回 `.gaoxia/story_overview_model.json`。作者在关系总览、时间线或世界要素卡片点击维护时，前端会把当前人物、事件、地点、道具、技能、组织/势力或时间线整理成带标记的 Markdown 维护块，写入“架构原文”草稿；保存后仍走故事文档接口。人物和技能落到 `character_state.txt`，时间线、事件和场景落到 `plot_structure.txt`，地点、道具和组织/势力落到 `world_building.txt`，并刷新知识索引、项目记忆和 StoryOverview 来源签名。下一次模型总览刷新会从这些项目设定文件重新生成结构化缓存。

## 7. Agent 执行状态与动作契约

Agent 执行现在会在项目目录保存可追踪的 workflow 文件：

```text
.gaoxia/runs/{task_id}/workflow.json
.gaoxia/runs/{task_id}/subtasks/*.json
```

workflow 记录这些内容：

- session 预检：项目目录、计划动作、模型配置、第二审查模型配置和失败案例库
- 主对话长文本输入：最新用户输入会完整进入 Agent 请求和线程保存，旧历史在前端压缩；超过 20000 字符的用户输入会由后端先筛掉明显无关、技术日志或网页样板段落，再按约 50000 字符分段导入项目资料库，并把资料标题加入本轮引用；路由、规划、brainstorm、技能整理和执行轨迹使用的是“摘要 + 原文头尾 + 资料引用”的压缩文本，避免把完整长文本直接送进模型上下文
- action 状态：`DISPATCHED / ACKED / RUNNING / SUCCEEDED / FAILED / BLOCKED / TIMED_OUT / STALLED`
- action 契约：进入条件、预期产物和失败策略
- action heartbeat：执行中定期刷新，旧任务可被标记为 `TIMED_OUT` 或 `STALLED`
- 子任务记录：写作、连续性审校、人物口气审校、可读性审校等子任务会记录允许产物范围和状态历史
- 产物校验：执行完成后检查本次 action 是否产出了对应 artifact 或章节正文
- `review_knowledge` 继承目标章节后，动作契约会按该章节可见的 Obsidian 笔记统计资料数量，避免用后段笔记数量误判早期章节资料状态
- 叙事状态账本里的章节任务卡会携带目标章节可见的 Obsidian 约束和执行状态；长篇稳定档案可用时，未入 Vault 的剧情债务、人物弧线、图谱问题，以及模型总览里尚未进入 Vault 的人物、事件、地点、道具、技能、场景和组织会生成维护建议并进入 Agent 规划上下文，Agent 路由 / 规划和自学习状态以维护刷新模式读取当前项目详情时会刷新这些建议，中高优先级建议会自动形成项目内待审草稿，草稿会带来源 ID、来源章节、人物双链或来源笔记路径；模型叙事编辑生成下一章合同时，会读取当前章和下一章按章节过滤后的 Obsidian 来源、必写项、禁写项、剧情债务、人物弧线和图谱风险；剧情债务和人物弧线的 Properties 字段会作为结构化账本来源读取，不要求作者把同一内容再写进正文小节

契约不满足时，执行会记为 `BLOCKED`；handler 异常记为 `FAILED`；整体执行成功后会把 `workflow_run` 作为 Agent 产物返回，便于从界面回到本地状态文件。

失败案例也会进入动作契约。`.gaoxia/learning/failure_cases.jsonl` 中同类 action 的历史失败会作为执行前提醒写入 workflow，重复失败会提高风险级别。

## 8. 自我进化报告与技能维护

技能区 `自我进化` 会把项目学习记录、Agent 轨迹、Prompt 历史和技能状态合并成一份只读报告。

### 报告来源

- 项目目录 `.gaoxia/learning/reviews.jsonl`：记忆候选、技能候选、章节低分修订经验
- 项目目录 `.gaoxia/obsidian.json`：Obsidian Vault 接入配置
- 项目目录 `.gaoxia/obsidian_sync.json`：上一次 Obsidian 同步摘要、笔记列表和过滤结果
- 项目目录 `.gaoxia/obsidian_drafts/`：Obsidian 维护建议保存的待审 Markdown 草稿；中高优先级建议会在章节保存、Obsidian 同步或章节上下文生成时自动进入这里，剧情债务草稿带来源 ID、来源章节和人物双链，章节档案草稿位于 `ChapterNotes/` 并带 `source_ids`、来源章节、来源正文签名、来源笔记、`chapter_summary`、`handoff_to_next`、`obsidian_required_missing`、正文摘录、地点 / 道具 / 组织关系和剧透边界，章节合同草稿位于 `Plans/` 并带目标章节、来源章节、合同目标、必须节拍、禁写动作和验收项，文风 / XP 草稿位于 `Style/` 或 `XP/` 并带来源章节、规则、适用范围、检查项、证据数和置信度，架构实体草稿位于 `Characters/`、`Locations/`、`Props/`、`Organizations/`、`Events/`、`Skills/` 或 `Scenes/` 并带对应人物、地点、道具、组织、事件、技能或场景档案摘要，未解析双链草稿带别名、来源笔记路径、来源笔记章节范围和剧透边界；章节提示读取真实草稿文件时，`create_chapter_note` 草稿会生成章节档案短预览，供后续章节承接摘要、交接和未完成必写项，`create_chapter_contract_note` 草稿会生成合同短预览，供目标章节在发布前参考合同目标、节拍、禁写和验收，`create_style_rule_note` / `create_xp_rule_note` 草稿会生成文风 / XP 短预览，供目标章节在发布前了解系统学习出的规则候选，`create_story_*` 架构实体草稿会生成档案摘要，供目标章节在发布前参考尚未正式入库的人物、地点、道具、组织、事件、技能或场景候选；Canvas file 节点关系进入章节提示时会显示可见笔记标题，减少原始路径对写作提示的干扰；来源章节范围不连续或多个开放式来源起点不同时不会合成过宽连续范围，会改用较晚可见的剧透边界；已解析双链如果来源笔记可见范围没有被目标笔记覆盖，会形成章节范围不匹配风险；未被人工改动的自动草稿会随图谱来源列表、来源内容和章节边界变化更新，人工改动过的草稿和保存草稿时遇到的既有人工内容不会被自动覆盖；章节提示会读取真实草稿文件里的章节范围、剧透边界和 `tags: [第58章起, 剧透/57]` 这类标签范围，也会校验维护 ID / 类型避免误用其它草稿正文；同一路径建议会沿用已有草稿状态；忽略同一路径建议后不会自动写草稿，恢复处理后会重新允许自动写草稿；草稿文件缺失时可重新保存；项目内 Vault 的系统草稿可自动发布并同步知识库；项目目录外 Vault、人工改动草稿、合并项、缺失项和低优先级规则仍需显式发布或确认；发布过的 Vault 笔记被移动或改名后会先按内容签名识别；新生成的维护笔记带 `gaoxia_maintenance_id`，发布到 Vault 前也会恢复缺失的身份字段，内容被作者改过但身份唯一匹配时也会改到新的 Vault 路径；章节档案保留 `source_ids` 时，移动、改名或改写标题后仍会按来源章节控制可见范围，并识别为同一章档案；没有唯一匹配或文件被删除时可重新发布；Vault 待更新项保存新版草稿时会在 `_updates/` 生成合并草稿，标出正式 Vault 笔记和系统建议路径，放入当前 Vault 正文和系统新版草稿；作者在 Obsidian 完成合并后可在自学习面板单条或批量确认，系统记录当前 Vault 内容并刷新 Obsidian 摘要和知识库；自学习面板会展示人工改动、保留人工内容、草稿缺失、Vault 笔记缺失、Vault 笔记已移动、Vault 待更新、Vault 合并草稿、确认 Vault 已合并、已忽略、恢复处理和批量恢复入口
- 自动章节档案草稿没有人工改动时，会随章节正文变化刷新；章节标题变化时迁移到新的 `ChapterNotes/` 文件名并移除旧自动草稿。人工改动过的章节档案草稿保留原文件和状态，不会被自动覆盖。自动发布过的章节档案在章节正文或标题变化后会进入 Vault 待更新状态，且不会把已发布的章节档案当成本章来源笔记引用自己。同步器会读取 `source_chapter_hash`，即使本地维护动作记录缺失，也能识别由系统生成但对应旧正文的章节档案；同步器也会读取章节档案保留的 `source_ids`，在作者移动、改名或重写标题后继续识别同一章档案。
- 项目目录 `.gaoxia/learning/style_xp_evolution.json`：章节保存后形成的系统学习版文风 / XP 状态
- 项目目录 `.gaoxia/learning/narrative_state.json`：章节保存后形成的剧情债务、人物弧线、章节任务卡、模型叙事审查、章节合同、Obsidian 维护建议和维护摘要
- 应用数据目录 `logs/agent_trajectories.jsonl`：执行计划、失败状态、章节产物 metadata
- 应用数据目录 `logs/prompt_history.jsonl`：模型调用失败、错误分类、用户处理建议
- 技能目录 `skills/` 和 `.skill_usage.json`：技能来源、使用次数、沉淀次数、更新时间

### 候选类型

- `skill`：适合沉淀成用户技能的写作流程或修订经验
- `memory`：需要作者确认后才能写进项目记忆的偏好、目标或约束
- `prompt`：适合进入提示词回归样本的执行失败或模型调用失败
- `review`：适合进入章节质量评测集的低分核验或自动修订样本

失败案例会保存 `severity` 和 `gate` 信息，后续同类 action 的契约检查会读取这些记录，用于执行前复核项目状态、章节目标和上一步产物。

写作回归现在包含内置黄金样本评测。回归报告里的 `golden_evaluator_benchmark` 会用模板腔、对白同质、连续性冲突和正常场景四类样本测试本地评审规则的召回率、精确度和误报控制，不会改正文或项目记忆。

### 技能维护

`GET /api/studio/skills/curation` 会给每个技能返回 `active / stale / archive_candidate` 状态。

- 内置技能默认保留
- 用户锁定的技能保留
- 有使用记录或沉淀记录的用户技能保留
- 长时间没有使用记录的用户技能会提示复查或归档

这套机制不直接改长期记忆、提示词方案或技能文件，只提供候选、证据和建议。

## 9. 旧稿接管导入

旧稿接管用于把已经在其它工具里写了一部分的小说接入项目。它和“资料导入”不是同一个功能：资料导入面向参考材料，旧稿接管面向正式章节正文。

### 导入行为

- 前端入口在作品列表顶部的“旧稿”；旧稿文件上传只支持 `.txt`，也可以直接粘贴正文。
- 前端会在读取前拒绝 30MB 以上旧稿文件，旧稿文件解析默认走本地文本抽取，不调用外部文档模型。
- 后端按 `第 X 章`、`Chapter X` 等章节标题导入旧稿；无法识别章节标题时，会把全文作为第 1 章，并在报告里提示作者确认。
- 当前项目最多接管 1000 章；超过上限时会拒绝导入并提示分卷或整理章节范围。
- 新建作品后，系统会逐章写入 `chapters/001.md`、`chapters/002.md` 等章节正文，把接续位置、上一章结尾、最近章节和写作边界写入 `core_seed.txt`、`plot_structure.txt`、`character_state.txt`、`blueprint.txt`、`global_summary.txt` 与 `checkpoint.json`，刷新本地知识库，并写入旧稿接管状态。
- 导入阶段不逐章触发模型核验，避免长篇旧稿导入过程中产生大量模型任务；后续可以按章执行诊断、续写、去 AI 或一致性检查。

### 可恢复状态

- 接管状态保存在 `.gaoxia/takeover/state.json`，原稿副本保存在 `.gaoxia/takeover/source.txt`，拆章结果保存在 `.gaoxia/takeover/chapters.json`，接管报告保存在 `.gaoxia/takeover/report.md`。
- 状态会记录 `task_id`、来源文件、原文签名、当前阶段、已写入章节、质量提醒和报告。
- 如果导入过程在写章节或刷新知识库前后中断，可调用 `POST /api/projects/{project_id}/takeover/resume` 继续处理；恢复时遇到已有非空章节正文会保留现有内容，不用旧稿覆盖作者已改章节；已完成的接管会返回已保存报告，并补齐缺失的报告或接续文档。

### 接口

- `POST /api/projects/takeover/import`：从旧稿创建作品，完成拆章、写入章节、刷新知识库并返回接管报告。
- `GET /api/projects/{project_id}/takeover`：读取接管状态。
- `POST /api/projects/{project_id}/takeover/resume`：按已有状态继续接管。

## 10. 项目迁移包

项目迁移包用于换电脑、备份和跨工作区复制作品。它和“导出整本”不是同一个功能：整本导出只面向阅读文本，迁移包面向继续创作。

### 包内容

- 导出结果是 `.gaoxia-project.zip`，默认写入当前作品目录的 `exports/`。
- 迁移包包含完整作品目录，包括 `project.json`、章节正文、设定文件、`.gaoxia` 项目状态、`.novel-history` 本地历史和 `knowledge.db`；项目目录内的 Obsidian Vault 会随项目迁移并保留索引、同步摘要和维护草稿；如果 Obsidian Vault 位于项目目录外，包内 `knowledge.db` 是清理过的打包副本，不携带外部 Obsidian 索引正文，包内同步文件也不携带外部笔记列表、摘要或预览，包内 `narrative_state.json` 会移除 Obsidian 维护建议和动作，`.gaoxia/obsidian_drafts/` 不会进入迁移包，包内 `project_distillation.json` 会移除外部 Obsidian 蒸馏条目并标记为需要重建；`.gaoxia/learning/*.json/.jsonl` 和其它 `.gaoxia` 状态文件会清理外部 Obsidian 资料分析、自学习复盘、失败案例等文本，遇到多段 JSON / JSONL 形式的状态文件也会按行写成迁移提示；Agent 线程和 `.gaoxia/runs/` workflow 状态保留对话壳、执行状态和非敏感字段，但 Obsidian 资料分析 artifact、维护 artifact、相关 trace / event 摘要以及 action / subtask 摘要会改成迁移提示，`.gaoxia/thread_context/` 索引导入后可重新生成。
- 包内会写入 `.gaoxia-project.json` 清单，记录迁移包版本、项目 ID、项目名、导出时间和 Obsidian Vault 是否在项目目录外。
- 已存在的 `.gaoxia-project.zip` 不会再次打进新迁移包，避免迁移包互相嵌套。

### 导入行为

- 导入接口接收 `.gaoxia-project.zip`，校验清单、压缩包路径和文件数量后，复制到当前应用工作区并注册进作品列表。
- 同一台机器重复导入同一个作品时，不覆盖原作品；系统会生成新的作品 ID 和目录名。
- 导入后会更新 `project.json` 里的 `id / name / path / updated_at`，并初始化知识库表和本地历史目录结构。
- 如果作品配置的 Obsidian Vault 在项目目录外，迁移包只保留项目内配置和章节学习状态；`.gaoxia/obsidian_sync.json` 会写成空笔记状态并提示重新同步，`.gaoxia/learning/narrative_state.json` 会清空 Obsidian 维护队列字段，`project_distillation.json` 会移除外部 Obsidian 蒸馏条目并标记为需要重建，`.gaoxia/learning/*.json/.jsonl`、Agent 线程、`.gaoxia/runs/` workflow 和其它 `.gaoxia` 状态中的 Obsidian 资料分析记录会改成迁移提示，不复制外部 Vault 原文，也不会携带外部笔记摘要、预览、维护草稿、线程上下文索引或 Obsidian 索引正文；导出和导入结果都会给出提醒，导入后按当前环境重新建索引。

### 接口与界面

- `POST /api/projects/{project_id}/migration/export`：生成迁移包并返回包路径和提醒。
- `POST /api/projects/migration/import`：导入迁移包并返回新注册的作品。
- 前端导入入口在工作台右上角“更多”菜单；导出入口在工作台“更多”菜单和作品菜单。

## 11. 这些模块和现有界面的关系

- 设置区：
  - 模型设置不再显示 Embedding 配置入口、篇幅能力手动选项或手动模型测试按钮；知识检索默认使用随 sidecar 打包的本地模型；保存写作设置后自动检测写作模型、本地检索和已启用的第二审查模型；旧配置和直接 API 调用仍可传入云端 Embedding 配置
  - 新增模型运行调度配置

  - 顶部“旧稿”入口支持 `.txt` 旧稿文件或粘贴正文接管
  - 每个作品的菜单可以导出完整迁移包，工作台右上角“更多”菜单可以导入 `.gaoxia-project.zip` 迁移包

  - `知识检索` 现在可以走语义检索

- `文风与DNA` 里还能直接搜索作者参考库
